# AA 成品矫正 Web 应用（本地 FastAPI 工具）

## 冷启动超时三根因（2026-09-14，重启后首访 33~99s → 2.7s）

**症状**：重启工作台后立即访问首页/作品页严重超时（实测 HTTP 首个请求 99.68s；进程内 `index()` 13.28s；warm 34.45s；warm 期间 index 33.12s）。修后：warm 6.27s、warm 期间 index 4.87s、冷 index 4.70s、重启后首个 HTTP 请求 2.67s、1258 章未译作品页 0.19s。

**根因①：三处磁盘缓存用内置 `hash()` 当指纹 —— PYTHONHASHSEED 跨进程随机 → 缓存 100% 失效**
`logic.material_frequency_cached`(materials_fp) / `material_chapters_cached`(mat_chapters_fp) / `extract_author_cached`(author_fp) 都写 `fp = str(hash(tuple(fp_parts)))`。实测同一文件：进程 A `-7706993486514785238`、进程 B `-3504677826830053700`、磁盘存 `5581069480730810060` —— 永不相等 → 每次重启重读全部 1703 个 `_汉化.txt`（224M 字符，HDD 4~8.5s）。已统一改 `logic.stable_fp(parts)`（md5，同 `_dir_top_snapshot` 口径）。**排查法**：凡 `work/*_cache.json` 里存 fp 的段，第一件事就是跨进程比对「算出来的 fp == 磁盘上的 fp」；`last_update_of` 早就修过同款 bug，剩下三处是漏网（`grep -rn "str(hash" aa_web_app/`）。

**根因②：未翻译作品的 `work_stats` 根本没有缓存**
`main.work_stats` 的「纯原文分支」（`not os.path.isdir(out_dir)`）既不读也不写 `stats_cache.json` → 每次冷调（每次重启 + 每 300s TTL 到期）都 listdir + 逐章读前 3 行，43 部未译作品合计 ~1.2 万次 open（1258 章那部单独 ~0.5s），且永不自愈。已加 `stats_cache.json` 的 `__src` 段（指纹 = `logic.dir_top_fp(aa_dir)` + chapter_order.json mtime + name_style）。**失效语义已单测锁定**：改任一 aa 文件内容 / 新增章节 / 改 chapter_order.json 都必须重算，其余情况零读取。

**根因③：`_dir_top_snapshot` 用 listdir+isfile+stat（每文件 3 次系统调用）**
全库 87 个 `aa/` 实测 **14.33s**；改 `os.scandir` + `entry.stat()`（Windows 上 DirEntry.stat 直接用目录枚举缓存的数据，零额外系统调用）→ **0.14s**，md5 逐字节一致（100x）。这才是 AGENTS 里那句「指纹验证本身要 stat 全部文件 → '命中'也全扫」的真凶——warm 的 `last_update refresh=True` 和请求路径的缓存缺失兜底都靠它。**教训**：Windows 上批量 stat 一律 `os.scandir`，别 `listdir+isfile+stat`。

**验证套路（零接触真实数据）**：① 临时目录造伪作品 + `main.cfg_of = lambda w: cfg` → 用计数版 `builtins.open` 断言「首次 3 次 open、二次 0 次」并测失效三条件；② 跨进程跑同一函数比对 fp/结果（hash() 类 bug 只有跨进程才暴露）；③ `import main`（warm 线程启动）后并发跑 `index()`，`while main._WARM_LOCK.locked(): sleep` 等 warm 结束再测一次 = 重启窗口的真实数字。**删除真实作品的缓存文件做复现要记清**（`last_update.json` 属可再生缓存，warm 会重建）。

- 模块 `aa_web_app/add_work.py` + main.py 两个路由：
  - `POST /api/parse-url` `{url, translate_intro?}` → `{title, chapter_count, intro_jp, intro_cn, intro_translated, chapters[], kind, r401_cid, site_key}`；简介日文→中文走 call_api，失败回退原文 + `intro_translated:false`（前端标注「可手动改」）

- **URL 分派**：`yaruobook.com/jp/net` → yaruobook_index；`rss.r401.net` → r401_index。**坑：`yaruobook_index.fetch_all_pages` 返回元组 `(entries, desc)`（desc=简介），`r401_index.fetch_all_pages` 返回纯 entries**——解包错了会拿 entries 当 dict 报 `'str' object has no attribute 'get'`。
- **r401 新网站拦截**：exlink 域名不在 `add_work.SUPPORTED_EXLINK_DOMAINS` → 422「该作品章节在新网站 XXX，解析器未覆盖，请手动处理」（解析阶段就验域名，提前止损不白下）
- **registry 动态追加** `main._append_registry_entry`：找 `def get(work)` 前最后一个 `    ),` 插入其后（保留 `\n}\n\n` 的 WORKS 闭合）。**路径值必须 `f'        {k}={v!r},'`（repr 自动转义）——用 `r"{v}"` 会把 `<repo-parent>` 的 `\a` 变成 BEL 控制字符破坏文件**（本次踩过，SyntaxWarning/乱码）
- **目录冲突防护（sujin_otona 事故教训，见坑区）**：work_id 目标目录已有非空 aa/汉化/raw 子目录 → 409 拒绝（**registry key 可能与目录名不一致**，如 sujin_otona 的 aa_dir=aaManga/大人のお店）
- **work_id 自动生成+只读（2026-08-30，6d85d0d6，用户纠正「作品ID默认自动生成，不再需要用户填（只读显示）」）**：① 前端 aw-id 改 `readonly disabled`（灰底），解析后自动填 `j.work_id`；② 后端 **api_add_work 忽略 body.work_id** 强制自动生成（防绕过）；③ 生成规则 `_work_id_from_title`：先 `_SITE_PREFIX_RE` 剥站名前缀（`re.compile("^(?:やる夫スレ本棚[^ |]*?)\s*[|｜]\s*")`），再 `[^\w\u3040-\u30ff\u4e00-\u9fff]+ → _`，禁 ◆★|｜ 等特殊字符（用户曾手动填 ◆tripcode 当 work_id 导致目录名带◆）。**防连点**：前端确认按钮 `disabled + .loading`（spinner 动画，style.css `.btn.loading::before`），后端注册段用 `with _LOCK:`（threading.Lock）串行化——异常路径自动释放，勿用独立 acquire/release。
- **api_add_work 全链路**：parse_url 再解析一次（防 URL 被篡改）→ 写 chapters.json → `_append_registry_entry` → work_meta → `api_reload()` → `TM.enqueue(download)`。测试会真实入队任务——测完必须 `task_manager cancel/remove` 清理残留任务（残留任务 work 不在 registry 会让 /api/tasks 500，见坑区 SystemExit）
- **简介汉化恒失败根因 = call_api 签名（2026-08-30，fbbdc91b）**：`aa_translate.call_api(system, body, ...)` **第一参数是 system、第二是 body**——translate_desc 曾写 `call_api(prompt, work_r18=...)`（prompt 当 system、缺 body）→ TypeError 被 `except Exception: pass` 吞 → 简介恒回退原文 + 前端「翻译失败」。修复=`call_api(system, desc, work_r18=)`（system 自建简介翻译提示词，含「不要输出日文假名」）。排查法：直接调 `call_api` 看异常，勿只看 translate_desc 返回 False。
- **标题剥站名前缀 `_clean_title`（fbbdc91b）**：yaruobook 分类页 `<title>` = 「やる夫スレ本棚2号館 | 作品名」，parse_url 原样返回 → 标题/简介带前缀。add_work.py 加 `_SITE_PREFIX_RE = re.compile(r"^(?:やる夫スレ本棚[^ |]*?)\s*[|｜]\s*")` + `_clean_title()`，parse_url 两个分支（yaruobook/r401）返回前应用。**存量清理**：registry 只改 `title=`/`html_title=` 行（值在行中，正则**不锚 `^`**）；work_meta 逐字段 jp_title/cn_name 替换（json 重写会改格式，可接受）。
- **yaruobook_index 分页修复（d54f545c + 36ad1168，cat=112 曾只抓 300→900→1258 条）**：WordPress 分类页分页参数是 **`paged=N`**（`?page=N` 被 WP 忽略恒返第一页）；PAGE_RE 原只匹配 `page=` 且不认 HTML 实体 `&#038;`（= &）→ 找不到下一页提前 break；继续条件「条数<20」对**每页 300 条的大分类**永不触发。修：`category_url` 用 `&paged=`；PAGE_RE 匹配 `(?:paged|page)=` + `(?:&|&amp;|&#038;)`。**二次修复（用户纠正「搞错了，共5页1200+话」）**：继续条件不能 `PAGE_RE.search` 取第一个页号——分页栏第一项常是「上一页」（paged=2），page 3 时搜到 2 ≠ 3+1 提前 break（曾误判 3 页 900 条）。改用 **`pages = {int(x) for x in PAGE_RE.findall(html)}` 收集全部页号，判 `(page+1) in pages` 才继续**。验证：cat=112 5页 1258 条全抓（page1-4 各 300 + page5 58，末条=第1話 在第5页）；cat=377 仍 5 条（单页不回归）。**教训：分页判断看「目标页号是否在链接集合里」而非「第一个链接的页号」**

## 删除作品（2026-09-03 实操 saki，设计见 doc/方案归档/作品列表页改版设计_2026-09-03.md v2 §3.1/5.4）

「彻底删除」一个作品 = 六处联动，**任何一处遗漏都留脏数据**。完整清单（以 saki 实测）：
1. **磁盘作品目录**——**禁 `rmtree aaManga/<id>`**（registry key≠目录名，40+/71 案例；saki_fc2 与 saki 共享 `aaManga/さーきー/` 根！）。基准 = cfg 的 aa_dir/out_dir/work_dir/raw_dir（绝对路径）。**共享根退化**：saki 四目录在根下、saki_fc2 四目录在 `*_fc2` 子目录——若 cfg 四路径 commonpath 落在别的条目也用的目录（如 `さーきー/`），**只能逐目录 rmtree cfg 精确值，不可 commonpath 一刀切**（会误删 saki_fc2）。删除前先列盘：`ls aaManga/<目录>/` 确认 fc2 变体与顶层 `work_fc2_*` 文件全保留。
2. **交付物**——`aaManga/交付HTML/<目录名>_汉化合集/`（2026-10-06 起是**文件夹**：整目录删，走 `main._deliver_artifacts(cfg)`）；**禁 `<目录名>_*` 裸 glob**（会连 `さーきー_FC2_试读合集*` 这类旧单文件一起删）。
3. **registry.py 条目**——工作台已有 `POST /api/work/<id>/delete`（内部 `main._remove_registry_entry`；`_append_registry_entry` 管追加）。**写 registry 一律走 `main._registry_path()`（= `registry.__file__` = app 实际 import 的那份；冻结 exe 里 = 数据根）**：别硬编码 `_SCRIPTS/works/registry.py`——冻结态那是 PyInstaller 解包目录，且被启动引导删掉（防子任务误命中），写它 = 删除永远在最后一步 500。**顺序铁律：先改记录（registry → work_meta → read_state）再删盘**，文件失败只留空目录可重试，记录失败直接 500 且不动任何文件；反之必留「文件没了、记录还在」的僵尸条目（列表里点不开又删不掉）。响应带 `failed` 列表（删不掉的路径，多为文件被占用，可停实例后重试）。用例 `scripts/tests/test_work_delete.py`。手写脚本删条目时的切片口径：从条目前注释行（`# ---- 站点N:`）到条目闭合 `    ),\r\n` 精确 find 切片，**断言段内含 `"<key>": dict(` 且不含兄弟 key** 再替换删除；CRLF 文件用 write_file 写 python 脚本执行（禁 patch），改完 py_compile + `grep -n '"<key>"'` 双校验 + `import registry` 验证 len 减一且兄弟条目完好。
4. **work_meta.json**——删 `<key>` 键（72→71）。**删后 grep 确认剩余匹配都是兄弟条目**（saki_fc2 的 cn_name 含「saki- 麻将少女(FC2续篇)」是合法保留）。
5. **.aaweb_progress.json**——删 `aa.{<key>}` 条目。
6. **热加载**——`POST /api/reload` → `{ok, works: 70}`，验证首页 HTML 里 `saki` 只剩 `saki_fc2` 的 data-work 属性。

前置核对：`TM.list_tasks()` 该作品无运行中任务；git 侧 aaManga 数据已出库（删除不产生 tracked 删除，无需 git rm）；knowledge/glossary 若被 `git add -f` 跟踪则提交时 `git add -A` 记录删除。不做自动 commit（用户惯例：删除类操作不自动提交）。完整实操另见 `references/delete-work-20260903.md`。

## 工作台性能优化（2026-09-05，重启首访 22s→<1s）
- **首页/index 冷扫三热点未预热**：`last_update`(12s, stat 全目录文件)/`r18_summary`(3.6s, 扫 prep)/`material_frequency`(3s)。`_warm_all_stats` 只暖 `work_stats`，需补齐。
- **last_update 磁盘持久缓存**（logic.py `last_update_of`，work/last_update.json）：指纹=aa/out 顶层文件级快照(mtime+size, **md5 确定性哈希**)。**禁用内置 hash()**（str 元组跨进程随机，磁盘缓存永失配）。`refresh=False`(访存/index) **零 stat 直接读缓存**；`refresh=True`(warm) 才 stat 重算写盘。
- **指纹用 md5 勿用 hash()**: JSON 读回 tuple→list 比较会永失配，只比 md5 str；内置 hash() 因 PYTHONHASHSEED 跨进程随机 → 磁盘缓存永久失效（曾致命中仍 10s）。
- **warm 不强制 refresh last_update**：last_update.json 是持久缓存重启后仍在，用访存(零 stat)即可；refresh=True 会全库 stat 11s（浪费）。

- **CRLF 判断陷阱**：`grep -cP '\r[^\n]'` 在 CRLF 文件返回 0（`\r` 后跟 `\n` 不匹配）→ **会误判 LF**。判断 CRLF 用 `python -c "d=open(f,'rb').read(); print(d.count(b'\r')-d.count(b'\r\n'))"`，=0 才是无孤立 CR。

**改 CRLF 文件另一个坑：`str.replace`/`str.count` 锚点缩进会误匹配（2026-08-29 translate_runner 实测炸过）**：CRLF 脚本统一用 `open(p,'rb').read().decode('utf-8').replace('\r\n','\n')` 编辑 → `.replace('\n','\r\n').encode()` 写回（写普通测试文件勿用 `open(p,'w')`——Windows 文本模式会转 CRLF，需 `newline=''`）。**锚点必须含精确前导缩进**：20 空格行**包含「12 空格+同文本」为子串**（20sp 前缀 index=8 处恰是 12sp 接字符）→ `count` 误判、替换拼接错位 → IndentationError。先 `assert text.count(anchor)==1` 再替换，或用整行/整块（带缩进）锚点；编辑完 `python -m py_compile` + `od -c` 核行尾。
- **⚠️ `grep -cP '\r[^\n]'` 判 CRLF 会误判（2026-09-05 踩坑）**：该正则匹配「\r 后跟非换行」——CRLF 里 \r 后面永远跟 \n，所以对纯 LF 和纯 CRLF 都返回 0，**无法区分行尾**。曾因此误把 main.py（实 CRLF）当 LF，用 `split('\n')` 读它导致多行替换串 matched 不上（count=0）。**正确判行尾**：`python -c "d=open(f,'rb').read(); print('CRLF:', d.count(b'\\r\\n'), '孤立CR:', d.count(b'\\r')-d.count(b'\\r\\n'))"`，或 `git show HEAD:files | python -c "import sys; d=sys.stdin.buffer.read(); print(d.count(b'\\r\\n'))"` 对比 HEAD 行尾（一致才行尾没被写坏）。改 CRLF 文件时读取规范化 `read().decode().replace('\r\n','\n')` 编辑、写回 `replace('\n','\r\n')`——**若原文件是 LF 却按此写回会把整文件转成 CRLF**（曾被误转 AGENTS.md，git diff 205 行假 diff：原本 107 行的 LF 文件变 107 个 CRLF，`replace('\r\n','\n')` 即可还原）。改前先确认 HEAD 行尾。
- **⚠️ 勿 `open(p,'wb').write(<复杂表达式>)` 一步到位（2026-09-05 把文件清成 0 字节）**：`open(p,'wb')` **先截断**文件，随后才求值 `.write()` 的参数——若 payload 表达式（如 `raw.replace(...).encode()`）抛 TypeError（bytes.replace 用 str 参数等），文件已截断但没写入 → **落盘成 0 字节**（`git status` 显示 M 且 `ls -la` 为 0）。**修：先 `payload = <表达式>` 算到变量，再 `open(p,'wb').write(payload)`；写完 `git checkout -- <file>` 恢复 + `wc -l` 确认行数没丢再重试。** 排查法：文件变 0 字节 + 报错在 write 行 → 几乎必是此模式。

## 翻译进程管理（统一任务管理器，2026-08-29 **已实现**）
- **方案+实现均已落地（6 commit，测试 226 全绿）**，详见 `references/task-manager-impl-2026-08-29.md`（组件/commit 序列/协议/坑①②③④⑤/端到端测试/运维实测）。方案先读 `doc/翻译进程管理方案_2026-08-29.md`。
- **⚠️ 工作台重启中断翻译任务（2026-08-31 根治）**：bat 重启 = `taskkill /f /pid <uvicorn>` 杀 8765——runner 是 uvicorn 子进程且同 console，被杀连坐 → 任务 crashed（现象：两个 running 任务同一时刻 finished、hb rc=None、心跳显示翻译/校对中）。**修复**：
  - `_start_task`/`ensure_scheduler` 的 Popen 用 `CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP` + `close_fds=True`。**勿用 DETACHED_PROCESS——它与 CREATE_NO_WINDOW 在 Windows 互斥，DETACHED 会忽略 NO_WINDOW → 测试/后台跑照弹黑窗**（本会话先加 CREATE_NO_WINDOW 但 DETACHED 还在 → 用户两次反馈"还在弹窗"）。重启不中断的保证 = runner 心跳自收尾（`task_report.finalize(rc)` 写 hb）+ 新工作台 scheduler reconcile 读心跳接管，不依赖进程树关系。
  - **reconcile 竞态（v3）**：进程退出与 `_watch`/finalize 写 hb rc 之间有异步窗口——pid 死 + 心跳无 rc 时**先不判 crashed**：`started_ts` 距今 <10s（收尾窗口）保持 running 交给 `_watch` 线程/下轮 reconcile，启动久且无 rc 才判真崩溃。v1 在 reconcile 里持锁 sleep 等 rc 会**死锁**（阻塞 `_watch` 的 `_finalize` 拿锁）；v2 查 `_watch_procs` 会被测试 tearDown clear 干扰。**测试偶发 FAIL 排查**：`test_task_manager` 连跑多次出现 crashed≠done——先查 reconcile 抢判，再查跨用例 `_watch_procs` 污染（tearDown 应 `p.wait(timeout=3)` 等收尾而非直接 kill+clear）。
  - **验证方法（杀父进程存活测试）**：父脚本（模拟 uvicorn）用 `subprocess.run(['taskkill','/F','/PID',str(os.getpid())])` 杀自己（Python 调 taskkill 无 git-bash `//` 转义坑），外层查 runner 存活（`tasklist /FI "PID eq N"` 输出 GBK 用 bytes 判断 `str(pid).encode() in stdout`）+ 心跳 rc（runner 自己写，不依赖调度器）。详见 `references/task-restart-no-interrupt-20260831.md`（含 reconcile 竞态 v1 死锁/v2 被 clear 干扰的失败路径、Popen 隔离测试、行尾不一致陷阱）。
- **⚠️ 两个必须在实现时记住的真 bug（运维实测踩出）**：
  - **本机 Windows 上 `os.kill(pid,0)` 对任意 pid（含存活）抛 `OSError: [WinError 87] 参数错误`** → `_pid_alive` 曾恒返回 False，**所有运行中任务被误标 crashed**。判活一律用 `ctypes.OpenProcess(0x1000,...)`（`81024090`）。「任何 Windows 判活 = OpenProcess，勿信 os.kill(pid,0)」。
  - **任务级 env 必须透传**（`params["env"]` → `_start_task` 里 `env.update(...)`），否则 web 调度器 spawn 的 runner 丢 `AA_FREE_MODE`/`AA_BACKEND`——重入队免费任务会误走付费链。CLI 加 `--free-mode`/`--env K=V`（`4f4f6d38`）。
