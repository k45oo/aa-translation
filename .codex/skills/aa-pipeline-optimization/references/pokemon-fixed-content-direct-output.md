# 固定内容「零模型直出」与「替换后是否还需翻译」判据（宝可梦专属链）

宝可梦链（`work_meta.pipeline=pokemon`）的目标流程：**术语替换（直接替换）→ 判断该行是否还需翻译 → 翻译（不注入术语表）**。
本文件是该流程的实现要点与实测坑；词表/机制的操作入口见仓库 `AGENTS.md`（补充术语.json 六段、pokemon_fixed 六轨、pre_terms）。

## 判据 A：替换后还需不需要翻译

把该行**被术语替换覆盖的跨度挖掉**，只看剩余片段：

- 剩余片段含假名（全角含 `ー`/`ヾ`，**半角片假名也算**）或非艺术汉字 → 送模型
- 剩余只剩 ASCII/标点/空白（含空）→ 替换完即译完，**直出**（本地照抄/写 ckpt `done`）
- **`・`(U+30FB 片假名中点)、`･`(U+FF65)、`゠` 先剔除再查假名**：它们落在假名码区（U+30A0–30FF），否则 `・技マシン…「A/B/C」`、`・「もちものセット」…` 这类道具/指令说明行替换后残留只剩标点，却仍被判「还需翻译」（实测两族各 11 行整族送模型）。

为什么不能用「无假名即直出」或现成的 `kana_runs`：

- `◎今回の編成（戦闘準備：>>1921）` **一个假名都没有**，全是日文汉字（今回/編成/準備）——按无假名判会原样出货 = 漏译。
- `kana_runs` 是**残留检测器**（已排除艺术假名 `スレ` 里的 `レ`、要求连串 ≥2），拿它判「还需翻译」会漏掉 `◎当スレwiki` 这类短假名行。判据要用「有假名就送」的粗口径，宁可多花 token。

实现：`pokemon_fixed.needs_translation(line, base=, work=, pairs=)` → `(需翻译?, 剩余片段, 命中列表, 替换后文本)`；`residue_of()` 用 `pre_terms.apply_hits` 的 `at`+`len(zh)` 反推未覆盖片段（不猜、可逐行解释，正好渲染给人工看）。

## 词源优先级（固定内容）

1. **本作设定 wiki 页面的逐行 jp/zh 平行对**（`pages[].blocks[]` 里 `k=b.text` 且 `jp`/`zh` 等长）——覆盖率远高于 `terms[].desc_zh`（实测同一批行 84.5% / 96.1% vs 26% / 52%）。
2. `terms[].desc` + `desc_zh`（术语表抽出的表条目）。
3. 表格块 `rows` **只有日文**、没有配对译文 → 配不出平行对，缺的就是这批。
4. `人工修正.json` 的 `修正`（键=日文原文行、值=中文）是**唯一手改入口**，优先级最高；`本地译名` 是名字来源。

## 匹配与自检（踩过的坑）

- **本作 wiki 轨必须排在 copy 轨之前**：copy 的语义是「整行原样照抄」，对曾经被判「无需翻译」的日文行照抄就是漏译。
- **译名一致性自检的三个假阳性**（写检查时必避）：
  - 括号写法不同（表里 `『王牌』`、wiki 译文里 `「王牌」`）→ 比较前**两边都去括号**。
  - `ハンター→猎手` 被 `モンスターハンター` 命中 → jp 是否真出现必须用 **pre_terms 的片假名邻接守卫正则**（`regex_for`）判定，不能用 `jp in line`。任何「源行含 jp 则输出必须含 zh」的校验都适用本条。
  - **只在引号内（『』「」【】《》）生效**：编成表标签 `敵陣→敌阵`（短形）会去和 wiki 正文里的长形「敌方阵营」较劲 → 整行误退模型；同理正文措辞差异不该算译名漂移。
  - **判据是「引号内容整体等于该 jp」，不是「命中位置落在引号内」**：短名子串会误拒**正确**译文——标准对里有 `つるぎ→斩`、`勝鬨→胜哄`，而它们在正文里只是 `「せいなるつるぎ」`（正译 **圣剑**）、`『撃槍姫の勝鬨』`（正译 **凯歌**）的一部分 → 整片正确的行被打回模型。实现：`_quote_spans(src)` 取引号内容 + `norm` 精确比对，命中即强制、否则跳过（本轨原来的 `_consist_rx` 邻接守卫正则 + `_quoted_at` 位置判据已随之删除）。上面那条片假名邻接守卫仍适用于别处的「源行含 jp 则输出必须含 zh」校验（如 `pre_terms` 的替换口径），只是本轨不再用它。
- **名字解析要兜底查合并词表**：本作 wiki 的家族条目常是占位写法（只收 `対〇回避`，没有 `対闘回避`），具体名的**说明**却与同族条目逐字相同 → 匹配时名字先查 wiki `names`，查不到再查 `merged_terms()`，就能靠「wiki 说明表 + 我们的名字表」拼出中文（整族 700+ 行）。
- **art 列位校验会把文本标点当图形笔画**：`（）、：-` 都在 art 笔画字符集里，于是 `こうげき：A-`→`攻击：A-`、`『…』…（0.85倍）…` 这类**纯文本行**全被误拒。修法：内容轨命中时按 `line_kind(line) == 'text'` 决定是否跳过 art 校验；混合行（AA 图形 + 文本单元）**不跳过**（单元夹在图形中，改宽会错位）。
- **宽度闸与项目口径冲突（两处闸，同一口径）**：共享 `aa_tm.guard` 一律不允许超宽，而 `scan_width`/工作台 `save_line` 对 text/mixed/header/skip **允许超宽**。中文说明常比日文长 → 固定内容直出在 art 行以外要放行超宽。只在 `pokemon_fixed.finalize()` 内放宽，**不要动共享 guard**（TM 复用行为会跟着变）。
  **第二处闸 = 整句模板自己的补位闸**：`_tpl_spans` 里 `_pad_to_span` 返回 None（中文比源 span 宽）时原先直接 `continue` 丢行 → `自陣：エクシア：速+1` → `自阵：能天使高达：速+1`（译名比日文名长 1 列）把**编成表整族 332 行**退回模型。模板正则锚定整行（`^\s*…\s*$`），能匹配的一定是整行、行内不存在需要对齐的 AA 图形 → text/mixed 放行（宽度最终由 finalize 的 `allow_overwidth` 定夺），art 行照旧丢。口诀：某族「模板明明在库却整族进模型」且译名比日文长 → 先查补位闸，别急着补词。
- **槽位解析需要合并词表**：`{名}` 这类模板槽位靠 `merged_terms()` = 通用 AA wiki 术语 ∪ 作品表 ∪ **本作 wiki 名字 ∪ 页面标题（`pages[].name→title`）∪ 平行对里的引号内容（`_harvest_quoted_pairs`）** ∪ 补充术语人工增量。少任何一路，本作借名个体（インコマン/できる夫…）解析不出中文 → 槽位回退日文 → 整行落回模型（症状就是「模板明明存在却不生效」）。
  **`_harvest_quoted_pairs` 必须有**：本作 wiki 正文里**早就有中文**的队伍名/道具名/潜能名/数值名，名字表原本只收 `terms[]` 与页面标题 → 这些照样进待补清单（`《遙か尊き星ノ紅玉》→《遥远尊贵之星之红玉》`、`『金魔女の陰謀』→『金魔女的阴谋』`、`夢うつつ→半梦半醒`、`かっこよさ→帅气`、`ライトニングシューター→闪电射手`；编成表族 200+ 行）。做法：同一条平行对里 jp/zh **两侧引号数一一对应**时，把引号内容当译名对；约束 jp 侧 ≥2 字、zh 侧不含假名、两侧不同（防把未译行/半成品当译名）。名字表 2900→3551 条，三章编成表+指令受族行 直出 53 / 送模型 3。`人工修正.本地译名` 仍用赋值覆盖（优先级最高）。
  **同一路词源必须同时接到替换轨**（`pre_terms` 词源 `本作wiki-引号`，开关 `AA_PRE_TERMS_WORK_WIKI_QUOTES=0`）——只喂名字解析/合并词表，症状是「模板族直出率上去了，编成表/道具/用招族仍把日文名送模型」：模板轨走 `merged_terms()`，替换轨只读 wiki `terms[]`/作品表/补充术语，两条路互不相通。实测接上后每章 +64~128 条可用词（`pre_terms.pairs_for` 的 src 计数可见）。
- **模板可选槽位**：`{尾?}` 编译成 `(?:(?P<gN>.+?))?`，缺省时中文侧该变量替换成空串；**只能放行尾**（非贪婪可选组在中段会吞掉后半行）。用途：`{名}に「特大のダメージ」！{尾?}` 收 `@1/@1～2` 与尾注。
- **程度副词不要做成全局词条**：`大きな/小さな/深刻な` 会命中正文散文。伤害结算的力度词写成**逐词模板**（`◎{名}に「深刻なダメージ」！{尾?}`），不要往 terms 段塞 `の→的`、`大きな→大` 这类通用词条。

## 模板引擎通用容错（引擎级；改前先读本节）

同一族「模板在库却整族进模型」，除了缺词，还有三类**写法变体**——放引擎里一次覆盖，比逐条加模板划算：

- **行首装饰 → 任意前缀**：前缀组从白名单式 `(?P<__pre>[◎○●・*‐‑–—―ー…\s]*)` 放宽成 **`(?P<__pre>[\s\S]*?)`（惰性）**，语义 = 「找到最早的、能让骨架匹配到**行尾**的位置」，前缀**原样回显**。理由：系统行常嵌在 AA 图形行里（`\|: : : : : :人…　◎アスカのレベルが「2」上がった！（Lv：30⇒32）`），白名单吃不到 AA 笔画。
  ⚠️ **必须同时加「廉价预筛字面量」**，否则性能崩：放宽后 86 条模板 × 全库 141 万行全要回溯搜索（实测单次全库扫描 **>7 分钟没跑完**）。做法：编译期给每条规则算一个 `need` = 骨架里最长的**无引号、无连接词**字面段（≥3 字；先从 `jp` 里 split 掉 `{槽位}` 与长连接词 `によって|により|を込めて|を込め`，再 split 掉引号字符，取最长片），`_tpl_spans` 里先 `need not in line` 直接 skip。`need` 是正则的**必要条件**，所以语义不变；实测全库 141 万行 **134 秒**扫完。
  影响面（放宽前先量）：带非空前缀的命中全库仅 201 行（181 行是 `・` 前缀），前缀 **kana-free 新直出 63 行**、**含片假名仍被 `match_tpl` 的整行假名检查拒**（保守：前缀含假名 = 疑似正文）；**无一例正常对话行被尾匹配吃掉**——前缀一含假名就先被假名检查拦住。想连含假名的图形行也直出，得给前缀开「艺术假名白名单」，默认不做。
- **`「」`⇄`『』` 互认 + 回显源风格**：AA 里属性/状态用 `「」`、潜能/队伍名用 `『』`，模板只写一种 → 编译期两种都收，输出用 `_echo_brackets(src, out)` 按**源行实际引号**改写（只在两侧引号数一一对应时改，否则原样返回，绝不猜）。**弯引号 `“”‘’` 也要算引号对**——人工填表常用弯引号，而标准表是 `「」`：引号数不匹配 → 引号序号对齐失效 → 译名自检把**正确译文**拒掉（实测用户填的 `“范围效果”` vs 标准 `全体技→全体招式`）。招式行骨架同步收 `◎『技名』…`；`_SLOT_TAIL` 的收尾引号要跟随源行（源行 `』` 就还 `』`），硬写 `」` 会把引号换掉。
- **连接词同义集**：`「…」` 后的 `によって` 也吃 `状態によって`（中缀）/`により`/`に`/`で`/`を込めて` → 编译成 `(?:状態)?(?:によって|により|を込めて|を込め|に|で)`（长词在前）。
  **放宽只做在「引号收尾紧邻连接词」的位置**（编译期 `re.sub(r"(?<=[」』])(?:状態)?<连接词>", <同义集>, escaped)`；lookbehind 只用于定位、不进 pattern）：全模板范围放宽会把字面里词内的 `に`/`で` 一起换掉，凭空接受乱码写法（`にんぎょう` ↔ `でんぎょう`）。开关 `AA_TPL_LAX=0` 回退（回退后 `により` 不接管、`によって` 照旧接管）。
- **中段插入、结尾缺 `！`、`を上げた`↔`が上がった` 这类结构变体留在数据侧**——语义不同、中文措辞也不同，加模板比放宽引擎安全（引擎只管「同一句话的不同写法」）。补这类模板的三条约束：
  - **宽泛变体必须排在具体模板之后**：整行锚定，`_drop_overlaps` 对「同起点同长」取**先注册者** → 「结尾无 `！`」这种更松的形态若写在前面，会把 `！` 吞进 `{尾?}`。数据段按文件顺序注册，所以新模板**追加到 `模板` 段末尾**恰好满足该约束。
  - 有了行首装饰容错就**不必再写 `◎` 重复条目**（旧表里成对的 `◎…`/非 `◎…` 是历史写法，新批次只写一条即可）；数字变体用槽位写成一条（`体力を{分}回復した` 收 1/2、1/4），别逐条硬写。
  - **`{尾?}` 是原样保留的**：尾注本身含日文（`（行動スキップ）` 这类）命中模板后输出仍有假名 → `match_tpl` 依铁律拒收、整行送模型。这**不是模板没命中**，别改模板；要让这类直出，得把尾注也做成词条。

**坑：整批配置被吞的入口必须留响**。`tpl_templates()` 外层 `except Exception: rules = []` 曾把一处类型错（把已编译的 `re.Pattern` 拿去拼字符串）变成**全部模板消失**，症状是「所有模板都不接管」，而单测全绿 → 白查一轮。规则：改完引擎除单测外**必须**用真实表在真实行上验一次（`match_tpl(line, table, merged_terms(work, work_dir))` 打几行看输出），并让装载失败打 stderr。

改完的回归口径：单测只证语法，覆盖要靠族级数字——跑 `gen_needs_render.py --gaps-all` 前后对比各族「直出/送模型」，或本 skill 的 `scripts/verify_family_direct_output.py --all-chapters`。

## 自检拒掉的整行：把输出**对齐**到标准表，而不是退回模型

本作 wiki 轨的「引号内译名与本章标准一致」自检会拒掉**本来能直出**的行：wiki 自己的中文口径与标准表不一致（`『対闘耐性』…` 的 wiki 中文是 `『对格耐性』…「格斗」`，标准表是 `对斗耐性`），输出里找不到标准 zh → 整行送模型。

**先量化「可救份额」（零 API）**：拿 `work/待补说明.md` 各族条目，按归一化行去查本作 wiki 平行对 —— `pokemon_fixed.norm(行) in work_wiki_sources(work)["lines"]` 命中即「wiki 有这条，是被自检/装配拒的，不是缺数据」。实测『潜能/特性』说明族 41%、【特性】说明族 53%、`・道具说明` 族 3%（那族主要是缺名字 + AA 噪音）。

修法是**对齐而不是放行**：按**引号序号**把输出里第 k 个引号的内容换成标准 zh（`_quote_spans(src)/_quote_spans(out)` 取两侧引号对，数量不等就整条不动；`_std_zh_map(pairs)` 只取非 `re:` 对，且只覆盖「源行第 k 个引号内容确实在标准表里」的那些），自检因此**由构造保证通过**，输出还与标准表统一。三处接线：整行/整段平行对（装配前对齐）、名+说明路（`zh_name` 标准表优先、`zh_desc` 同样对齐）、说明内引号名。开关 `AA_QQ_ALIGN=0`。

- **必须在宽度补位之前做**：换名会改宽度；先补位再改名 = 行宽与源不一致（art 行直接拒）。凡是「事后改输出文本」的机制（对齐/还原/规范化）都要排在 `_assemble_ww` / `_pad_to_span` **之前**。
- **靠位置对齐的机制必须先归一输入侧的引号风格**：对齐靠「第 k 个引号」配对，两侧引号数一旦不等就**静默整条不动**（不报错）。人工填表/译文常用**弯引号** `“”‘’`，而标准表与 wiki 是 `「」`/`『』` → 数量对不上、对齐失效、自检随即把这条**正确**译文拒掉（症状：手填的说明行仍送模型）。修法：把弯引号也纳入 `_quote_spans` 的 `_QUOTE_OPEN/_QUOTE_CLOSE`（**不要**加进 `_BRACKETS`——那是「比较译名时去括号」的口径，加上会改变 `_names_consistent` 的行为）。以后新增任何引号风格（纸引号、全角方括号…）都要同步这两处，否则对齐/回显/整段相等三条判据会各自静默走样。
- **反直觉效应：加词源会让这个自检变严**，说明类族的送模型数可能不降反升（实测加了引号名与人工译名后『潜能/特性』说明族 751→900）——别读成引擎改坏了，先按上面的方法量一遍「可救份额」。
- **族级判据（顺序别错）**：模板族整族回落 → 先查写法变体（行首装饰/引号/连接词）；说明族回落 → 先量「wiki 有没有这条」（**原键/归一键都查不到 → 才是人工补整句；查到 → 走引号序号对齐**，见上「全库待补清单怎么读」）；单个短片段残留 → 补词条/`本地译名`。顺序对了，一次引擎改动抵几百条人工条目。

## 固定行落在哪一层（选错就白做）

- **无变量的整句 → `补充术语.json` 的 `terms` 段**：模板编译器要求 jp/zh **都含 `{…}`**，纯固定句（`こうかはばつぐんだ！`、图鉴进度行）写进模板段会被**静默跳过**；人工 terms 条目允许 ≤60 字整句，正好收这类。
- **带变量的骨架 → `模板` 段**。同一族要写成**通用形态**：`【技x4：…】` 只覆盖 103 行，`【技x{N}：{A}】` 才是全族（x4~x8 共 690 行）——写窄的症状就是用户说的「技能明明都翻好了却还进模型」。
- **说明来自 wiki 的行 → 本作 wiki 轨**，**三种形态都要认**：`『名』…说明`、`【特性】名…说明`、**`・名…说明`（道具/指令说明行，如 `・ボコのみ…体力が満タンの時…`）**；不要再做成模板。第三种的坑：zh 侧拆头函数原先只认 `』`/`】` 收尾，`・{名}…` 行返回 None → 整行静默回落模型（wiki 里明明有平行对）；补一条「头部 = 第一个 `…` 之前（且前半含 `・`）」即可，同时把该形态登记进 descs 表。
- 模板的「全有全无」语义是白拿的：任一槽位没解析成中文 → 输出残留假名 → `match_tpl` 拒收 → 整行回落模型。要表达「所有招式都翻译了才直出」不必另写逻辑。
- **命名族（`対◯回避/耐性/迫撃/反撃`）按语料实际出现的组合生成具体词条**，属性单字走 `槽位『类型』` 的同宽短形表（闘→斗、炎→火、龍→龙），动作词 迫撃→迫击、反撃→反击。比正则规则稳：整行命中与编成表尾巴槽位解析两条路都生效。
- 短句替换**不要为了省事加通用词条**：`の→的`、`大きな→大`、`済→已`（`経済/返済` 会被误伤）一律别加，收进整句条目或模板里。**组合词成员同理**：`ダブル`（双+其他）不加整词条——加了会吃掉 `ダブルオーガンダム`（00高达）、`仮面ライダーダブル`（假面骑士双骑）这类含它的专名。短名与长名共存（`マジンガー` / `マジンガーZ`）靠「同表内长词优先」保序，但**片假名邻接守卫的收尾 lookahead 只挡片假名、不挡 ASCII 后缀**（`Z` 不算片假名）→ 落表后必须用 `apply_hits` 在**含该写法的章**上实测两种形态各一次，别只信排序。

## 缺词导致「整行回落」的排查

模板在库、命令也对，但整行仍送模型 → 九成是**槽位里某个词不在表里**。把该行丢给 `pokemon_fixed.match_tpl(line, {}, pokemon_fixed.merged_terms(work, work_dir))` 单测，一眼看出槽位解析没解析。**用 `pairs_for(base)` 做单测时必须挑真正含该行的那一章**：pairs 按章语料过滤，随手换一章会得到「词表里明明有、却解析不出」的假结论（实测两次误判都是这个原因）。典型缺词：

- 官方对照漏收（`みきわめ`、`白いハーブ`）→ 补 `补充术语.json` 的 terms 段。
- **官方对照用全角写法**（`１０まんボルト`）而原文是半角（`10まんボルト`）→ 字符串比不中，按半角补一条。
- 名字不在本作 wiki（借名个体另一种写法，如 `ニュージャージ` vs `ニュージャージー`）→ 进待补清单人工补。
- **先分清「真缺词」与「查表键对不上」**（两者症状一模一样）：本作 wiki 页常写平假名（`…味方1体の「こうげき」を上げる。`、`1/試`），章节正文写汉字短形（`…「攻」を上げる。`、`１/試`）→ 同一行的**整行键与说明键都查不到**（实测某说明族 top40 里 26 条栽在这，而 wiki 里其实有这条）。修法是归一**查表键**、不是补数据：建索引时原键与归一键同时写（`norm_alt()` = `norm` 之上再加两层：① 属性表记 こうげき→攻/ぼうぎょ→防/とくこう→特攻/とくぼう→特防/すばやさ→速/めいちゅう→命中/かいひ→回避/たいりょく→体力；② **波ダッシュ分歧** `〜`(U+301C)/`～`(U+FF5E)/`~` 统一成一种——wiki 页与章节正文各写一种，`強化（1.1〜1.4倍）` vs `（1.1～1.4倍）` 同样两键都不中，实测同一族 top40 里 27 条是这个），查表走 `wiki_lookup()` 两段回退；**只当查表键，不改落盘文本**。日文源的两类「同内容不同码位」分歧（假名 vs 汉字表记、波ダッシュ vs 全角チルダ）都是**先查表键归一**、不是补数据——补数据只会补出一条谁都撞不上的死条目。判据：在 `work_wiki_sources()[...]['lines']` 里「原键不中、归一键中」→ 引擎问题；两键都不中 → 才是真缺数据。

## 全库待补清单怎么读（先归因，再决定补法）

同一个族里混着**三种缺口，补法完全不同**——按条目总数估工作量会白花时间：

归因做法（零 API 近似）：用**并集词表**（`merged_terms` ∪ `补充术语.extra_pairs` ∪ `官方对照`）对清单行做最长优先替换 → 取残留里**含假名**的片段（纯汉字片段可能是已译中文，不能算缺词）→ 按「单个短片段（≤8 字）」与「多片段」分桶计数。现成脚本：本 skill 的 `scripts/attribute_gap_list.py --work <id> [--family <族>]`（读 `work/待补说明.md`）。
**「这条为什么没直出」用另一个探针**：`scripts/attribute_gap_reason.py --work <id> [--family 族片段] [--limit N] [--detail]` 按判定顺序逐条复算，归入 ①正则不认 / ②查表键不命中 / ③切不开 / ④`_ww_ok` / ⑤译名自检拒 / ✅其实可直出 六类——②先修引擎（键归一），⑤先对齐，两键都不中才是补数据（实测靠它把「说明族没降」拆成「26 条键对不上 + 21 条口径冲突」）。
**写新探针前先查现成的**：本 skill 的 `scripts/`（`attribute_gap_list` / `attribute_gap_reason` / `verify_family_direct_output` / `audit_sent_lines`）与仓库侧 `scripts/tools/gen_needs_render.py --gaps-all` 已覆盖「全库清单 / 逐条归因 / 族级计数」三件事。重写一份的代价不是多打几行，而是判定口径分叉（`classify` / `needs_translation` / 各轨自检三层措辞），自己的探针与生产数对不上时还得回头查是不是探针写歪了。

- **单个短片段 = 缺名字/词条** → 补 `人工修正.json` 的 `本地译名`，或 `补充术语.json` 的 `terms` / `works.<作品>.terms`：一条解锁几十行（实测 `星ノ紅玉`×71、`その他`×36、`宙に浮かび上がる`×13、`足引き沈む泥の沼`×10、`かっこよさ/たくましさ/かしこさ` 这类数值名）。
- **多片段 = wiki 里措辞不同的整句说明** → 只能整句人工补 `修正`（键=日文原文行、值=中文）。**别指望补词收掉，也别写模糊匹配**：实测 640 条 `『潜能名』…说明` 里「与 wiki 同骨架、只有「」占位符不同」的是 **0 条** → 占位符宽容匹配不值得做（先量再决定）。
- **AA 画行噪音**：`・道具说明` 族约 1/4 是 AA 图形行（`・` 撞图形）→ 读清单先剔噪。
- 高频缺口用 `md` 里的「次数」列排序即可定位；只出现在个别章的 1 次条目可以留给模型。

## 用户手填的 `待补说明.md` → 落库（清单的闭环）

用户会在 `work/待补说明.md` 的「中文（填这里）」列直接填。落库前**先分四类**（同一份清单里混着四类，整条当译文入库会写坏表）：

1. **只填名字**（源行是 `『X』…`，值是一个名词，常带 `『』`/`《》`）：→ `本地译名`。**值要剥掉引号**——引号来自源行，留着会变成 `『『名』』`；用户把名字连括号写出来，意思就是「这个引号里的名字」。
2. **整行说明**（源行是 `【特性】名…说明` / `『名』…说明`，值是完整中文句）：→ `人工修正.json` 的 `修正`，键=源行、值=中文。
3. **指引而不是译文**：`（角色名）倒下了！`、`（角色名）接受了『熟達攻撃指令』…（熟達=熟练，全開=全开）`、`（aa不变） …` 这类是**要你去补名字/补词条/靠引擎**，别整条写进 `修正`。`（aa不变）` = AA 图形保留、只翻后面文本（图形保留由行首装饰回显负责）；填里为方便人读加的括号标注落库时去掉。
4. **一个值写了两种写法**（`A和B都是X`）→ 两种写法各建一条 `本地译名`。

键的构造与校验（`修正` 最容易白做）：

- **键必须等于引擎看到的 `seg`，不是整行**：`match_work_wiki` 按 `_AB_SEARCH → _ST_SEARCH → _DOT_SEARCH` 顺序取锚点，`seg = line[m.start():]`。嵌在 AA 图形行里的说明行，`修正` 键要写**锚点之后那一段**（`【特性】…`/`◎…`），AA 前缀留给引擎回显（用户填的 `（aa不变）` 正对应这点）。落库脚本用同一顺序切一遍键即可。
- **插完逐个键回语料验一次**（全库扫 `norm(seg) == norm(键)`）：清单里的行可能被编辑器**截断**（少句尾），截断键永远命不中也不报错，症状是「用户填了却还送模型」。
- **填值与既有 `本地译名`/本作 wiki 冲突时不要自动覆盖**：库里的是人工早先定的口径（还影响别处），当次填的可能是随口意译。列出来让用户二选一，别顺着最新一条改表。
- **用户明确禁止某词条时，个别行的需求用整行 `修正` 满足**（键=该行源文）：例如 `ダブル` 定为组合词、不加整词条，就用一行 `修正` 收掉 `◎ダブルは「きあいのタスキ」で、皮一枚で踏ん張った！@0/1`。注意 `修正` 是**整行精确匹配**，尾注一变就命不中——只有尾注固定的行才值得这么做。
- **用户给的路径与仓库路径不同 ≠ 不同文件**：作品目录常有符号链接别名（同一份 `待补说明.md` 在两个盘符路径下都在）。先比对 `size`/`mtime`、或看该目录是否 symlink，再决定要不要复制，别当两份内容去 diff。

## 验收流程（用户要求：先看判据，再落地开关）

1. 先出**标记渲染页**：`python scripts/tools/gen_needs_render.py --work <id> --base e1,e2 [--gaps <path>]`——左侧状态列（直出/送模型）+ 替换高亮 + 残留片段明细 + 「只看直出/只看送模型」筛选、切章按钮。
2. `--gaps` 导出的待补清单**只列「本该由固定内容直出却缺失」的族**（`【特性】名…说明` / `『潜能名』…说明`）；把全部送模型行列进去会被台词噪音淹没，清单没法用。
   **全库缺口清单**用 `gen_needs_render.py --gaps-all [--limit N]`（不渲染 HTML，全库 400+ 章约 13 分钟；`--limit` 先抽样）：按 14 族分节导出「次数 | 日文原文 | 中文（空白待填）」，落到 `work/待补说明.md`。渲染页模式只适合 3~5 章。
3. 人工确认判据准确后，才接生产开关：`prefill` 写 ckpt `done`（替换后残留为空也走这条路）+ 翻译/校对停「术语对」注入（保留 さん→桑、语境、角色译名、章节简介；校对 P1 词表护栏不动）。
4. 全库量测：`scripts/tools/gen_needs_render.py` 的判据函数可复用做抽样/全库统计（400+ 章约 15 分钟），先抽样再全量，别只报单章数字就下结论。**每次量测记下对象数**：作品可能在量测之间被别的进程加了章（实测同一部作品两次量测 416→444 章），raw 总数不可跨次比——只比「按族/按判据的比率」并注明两次章数，否则会把新增内容读成改动效果。**窗口内第三方默认值变化同样要归因**：同一仓库常有别的会话同时改（实测另一次会话把艺术行否决功能默认打开，4 章里「可翻译行」4,829→3,580，级联到全库直出少一万四）→ 报数前用对应开关两臂各跑一遍（`AA_<该功能>=1/0`），把位移记到那条开关名下；一般化的做法见 skill `bulk-pipeline-changes` §二。**「量测跑到一半报错、traceback 指向自己没改过的文件」= 撞上别人的半成品编辑**：`python -c "import <module>"` 验自洽后原样重跑该作业，产物整份重跑，提交只加自己改的路径（详见该 skill §五）。**自己中途改数据/代码同理**：`tpl_templates()`/词表都在进程内缓存，量测启动后再改 `补充术语.json` 会让同一份产物前后口径不一 → 先杀掉该作业再改，或改完整份重跑；半程数字只能定位，不能当验收。
5. **按族验收**：用本 skill 自带的 `scripts/verify_family_direct_output.py --work <id> --base e1,e2 [--family <正则>] [--all-chapters]`（每族 直出/送模型 计数 + 一正一反样例，判定复用 `gen_needs_render.classify`，与渲染页/prefill 同一口径），比报总数有用——用户往往**点名族**来验收（「这批可以直出」「这个还在进模型」），族级计数才能直接回答。
6. 渲染页可达 3~4MB / 1.4 万行，浏览器**截图会超时**；改用 DOM 核验：`.aa` 左边界是否唯一（列对齐）、`.row.d`/`.row.s` 计数、筛选与切章按钮点完的 hidden class。别因为截图失败就以为页面坏了。

## 生产开关落地（判据 A 直出 / 停术语对注入）

判据确认后接的两条开关，落点与坑：

- **判据 A 直出 = 在 `prefill` 里加一路 `hit`，不改 `aa_translate` 核心**：`match_line` 未命中且 `AA_FIXED_PRETERM != 0` 时，`needs_translation()` 判「不需翻译且有替换命中」就造 `{"track": "preterm", "zh": 替换后文本, "no_art": _no_art(line)}` 交给**同一个 `finalize()`** → 四重护栏/pad/写 ckpt `done`/命中痕迹 `fixed_hits/` 全部复用，回退只需关一个 env。统计要新增 `hit_tpl / hit_workwiki / hit_preterm`，否则日志看不出这三路在生效（只报 `struct/whole/rule/copy` 会让人以为改动没上车）。
- **`prefill` / `normalize_chapters` 调 `match_line` 必须显式带 `work=` 与本章 `pairs=`**：本作 wiki 轨和模板槽位都靠它们；漏传的症状是「命令跑通、命中数明显偏低」。`normalize_chapters` 的源行模板回填同理——只给 `wiki_terms()` 会解析不出本作借名个体，白名单一行都回填不上。
- **停术语对注入是两处，不是一处**：翻译侧 `aa_translate.glossary_prompt_hint` 的【术语表】段 + 知识库 `work_memory.memory_hint(..., with_terms=False)` 的【作品记忆-固定译法】；校对侧 `refine_aa._load_gloss_hint` 同停。**但校对的 P1 词表护栏必须留**——它拦的是「模型把已落地标准译名改回去」，与注入无关，是另一条路。
- **停一块注入前，先查它是否和别人共用条件分支**：`さん→桑` 那条通用规则原本写在 `if pairs:` 块内，术语对一停就**被连带停掉**（实测 hint 直接变空串）。修法：把它移到 `if pairs or <本链判定>:`，非本链作品行为不变。任何「关掉一段 prompt」的改动都要按同样方式扫一遍同块内其它规则。
- **流水线判定要按 work id 缓存**：`WORK_ID` 是 runner 在 import 之后才设上的，只缓一个布尔会把「还没设作品时算出的 False」一直用下去 → 缓存写成 `{work: bool}`。
- **A/B 自证**：把 `work_pipeline.pipeline_of` 临时 monkeypatch 成返回空串，同章再跑一次，hint 字数应从 72 回到 1300+（证明行为差异确实来自本次改动，而不是别的因素）。改动前后各跑一次，比「看着像生效了」可靠；非本链作品也顺手跑一次，确认没被误伤。

## 收尾检查

- **新增工具脚本必须重跑** `scripts/tools/gen_inventory.py` + `scripts/tools/gen_interface_docs.py`，否则 `test_interface_docs` 两条必红（这是自己引入的，不是既有失败）。
- **顺序不能反，且「只加 env 变量」最容易漏**：`gen_interface_docs` 的 per-file env 列表读的是 `_inventory.json`（不是现场扫 AST），所以新加一个 `AA_*` env（哪怕只加在既有文件里）必须先 `gen_inventory.py` 再 `gen_interface_docs.py`；只跑后者时该 env **静默缺席**接口文档，而 `test_interface_docs` 依然绿（它校验的是文档与 inventory 一致）。落完 grep 该 env 名确认进文档。
- **区分既有失败**：全量测试红了先 `git stash push -- <自己改的文件>` 复跑失败用例，确认哪些与本次无关，再恢复（`git stash pop`）——不要顺手去修别人的红。

## 数据批次入场（补充术语.json 批量插块）

按族补词条/模板用脚本插块（在 `"模板": [` / `"terms": [` 之后插格式化 JSON 行，幂等键=jp 已存在则跳过），每次插完必须**读回校验**：

- **重复段陷阱（会静默丢词条）**：脚本用正则匹配 `works.<作品>.terms` 时若命中「第一个 <作品> 段」，会再造一个同名段；JSON 同名键 `json.loads` **只保留最后一个** → 上一批的条目全部消失（症状：新加的生效、上一批的没了）。插完 `grep -c '"<作品>": {'` 必须 ==1；发现两段就按括号配平切段、按 jp 去重 union 合成一段再写回。
- 插完先 `json.loads` 校验语法 + 打印 `len(terms)/len(模板)` 与预期比对，再 `gen_pokemon_aa_wiki.py --build`（通用 terms 靠生成物 术语表.json 才被 `wiki_terms()/tpl_terms()` 读到；作品专属 terms 由 `pre_terms.extra_pairs` 直读）。
- **族规模先量再写**：`grep -h -o "…" *.txt | sort | uniq -c | sort -rn` 拿到全库形态分布，再决定写通用骨架还是逐条（见上「落层」）。写窄的症状就是用户说的「明明都翻好了却还进模型」。
- **插完模板/词条逐条用真实行验一次**（`match_tpl(line, load(work, work_dir), merged_terms(work, work_dir))`），并把结果分三类归因：①命中且输出无假名 = 成了；②未命中且槽位落在**名字**上 = 缺词（补 `本地译名`/`terms`），**不是模板问题**；③命中但输出仍有假名 = `{尾?}` 尾注含日文，按铁律该送模型。三类混着数会得出「模板没生效」的错误结论。
- **人工维护的 JSON 一律外科式文本插入，禁 `json.dump` 整体重写**：`补充术语.json` / `人工修正.json` / 工作知识库都有自己的缩进与换行风格（还有 LF/CRLF 之别），`json.dump` 会把全文重排——实测加 1 条 = 5882 行 diff，真改动被评审噪音淹没。做法：`open(..., encoding="utf-8", newline="")` 读原文 → 断言待插片段在全文中唯一 → `str.replace` 插入 → `json.loads` 校验 → 原样写回（换行不动）。已经提交了重排版：`git checkout HEAD~1 -- <file>` 还原 → 再外科式插入 → `git commit --amend` 收进同一提交（别为格式单开一个 commit）。
- **用户给的样例常是「中文填充 + 日文骨架」**（如 `◎貴婦人は「隐形岩」の伤害を負ってしまった！@15/16`）——名字/招式是中文、句法留日文。写模板前必须回语料捞**真实原文行**，别照样例字面当 jp。
- **官方道具/招式名先核权威（52poke）再落表**：官方中文可能与直觉不同（实测 `とくせいガード` = 「特性护具」而非“护罩”、`クリアチャーム` = 「清净坠饰」而非“通关护符”）；本地 `官方对照.json` 缺条目时联网核，并把依据写进词条 `note`。
- **用户填的清单要按四类落库，别一把当名字**：① `『X』…` 形态且填的是名字 → `本地译名`；② 整行说明（含嵌在 AA 图形行里的）→ `修正`（键 = `match_work_wiki` 锚点切出的那一段，脚本里用 `_AB_SEARCH/_ST_SEARCH/_DOT_SEARCH` 同序切，别用整行）；③ 用户写成「（角色名）倒下了！」这类**引导语**的 → 什么都不写，那是告诉你「模板已够、只缺名字」；④ 用户填的「中文 + 日文骨架」样例要回语料捞真实原文行再落模板。落完必须**逐条回扫语料**确认键命中（填表可能被编辑器截断，截断的键静默不生效），并逐行跑 `classify` 看是否真变直出。用户填的值与既有表冲突时（`メタナイト` 填梅塔骑士 vs 库里金属骑士）**先问再改**，别自作主张覆盖。
- **给用户「补缺口」的草稿要分级标依据、并明确哪些是派生**：每条注明来源——wiki 长名的**缩写**（`星ノ紅玉←遙か尊き星ノ紅玉→《遥远尊贵之星之红玉》`，回复里**明确标「缩写派生、非 wiki 原文」**）、wiki 平行对原文（`その他→其他`）、招式列表（`いてつくいしせん→冻光之矛`）。无依据的（同名歧义如 `ダブル`、疑似截断的招式名）**留空、单列「待你定」**，绝不塞进表里当已确认。用户要的是「能扫一眼改掉的草稿」，不是替他拍板。
