## AAHub 本地数据源事实（已实测）

- **本地全量**：`<repo>/AAhub/`（2.3G，15,022 个 .mlt，AAEdit 模板格式）——用户已下载，无需爬。线上另有整库 zip `https://dataset.aahub.org/datasets/mlt_v32_1.zip`(544MB) 与增量 `api/mlt/changes?limit=2000`。**⚠️ 2026-10-10：本地 AAhub 已随搁置方案收尾删除**，要复现本实验须先下线上 zip
- **文件编码/格式**：CP932(SJIS)；`[SPLIT]` 分隔条目，条目首行常为 AA 名（【基本】等），正文 = `\r\n` 分隔的 AA 行（U+3000 空格）；首部一条 `最終更新日`
- **目录即元数据**：层级 `<五十音>/<行>/(A・0・記号 等)/<作品>/[分类子目录/]<角色>/<角色>NN（姿势）.mlt`，例 `か行/か/艦隊これくしょん～艦これ～/駆逐艦/島風/島風01（基本）.mlt` → 作品=艦これ、角色=島風、分类=駆逐艦。深度 1-10 混排，2ch/ 分支=原创派生角色（やる夫系）无外部作品
- **R18 信号**：路径含 `(R18)`/`R18`/`エロ`/`全裸`/`本番` 等关键词（53 目录/1116 文件含 R18）；`島風（R18）/` 与普通 `島風/` 目录并列
- **编码坑**：mlt 是 CP932 非 UTF-8，open 必须 `encoding='cp932'`；行尾 rstrip 用 `' \u3000'`

## 匹配引擎（原型 `scripts/tools/aahub_db_proto.py`）

- `AAHdb.build(mlt_dirs)`：行 norm(U+3000→空格) + **去空格 6-gram 倒排**（core() 平移不变签名）；14k 行库 0.7s build
- `best_art_span(line)`：候选精排 difflib 含空格相等段（autojunk=False），**score=段内非空格字符数 ≥ 阈值**（防空格海伪命中——纯台词行因前导空格柱假命中是头号陷阱）；返回 (score, art列区间[start,end), DB行, 等长)
- 查询 10-50ms/行（倒排+精排）
- **记分必须扣除空格**：命中主要来自「前导空格柱+行首结构」，数含空格连续格会把台词行也命中；非空字符连续匹配才是真锚点

## 锁定决策（10 项）

1. DB = **增强信号+否决层，非替代启发式**（未命中仍走 v3/is_text_line 兜底）
2. 引擎架构 C：整行精确哈希免费先查 + 锚点近似为主力召回
3. 记分 = 非空格锚点（v2 再叠 x 坐标列偏移）
4. 插入位置：DB 命中即权威 art 边界；未命中回落 v3 → 启发式
5. 防伪：命中段非空字符下限 + 不与已确认 text 台词行冲突
6. 失配：**块级插值**——同 (file,blk) 连续命中 ≥3 行，run 内失配行也标 art
7. 先瘦库后胖库两阶段
8. 台词衔接：DB 直接产出 text 段，走现有 `MIXED_SEG_RE 行号_段号` 段级翻译通道
9. 元数据主键 = AAHub **日文源名**；`aahub_作品映射.json` 渐进式缓存（AAHub 日文→registry id），不做全量人工映射
10. 瘦库范围 = **roles.json 全部角色及其作品 + 同作品 AAHub 有而 roles.json 无的角色**（作品级兜底）

## 块级匹配可行性验证（2026-09-05 实测）

**核心结论：块级匹配可行，关键不是「块 vs 行」而是「用什么特征」。**

岛风基准（entry_20990 2406-2434,正文 29 行立绘块）vs 岛风01(基本).mlt 全部 200+ 姿势块（SPLIT 条目）：
- **几何特征（行宽密度直方图 Jaccard）→ 失败**：blk64 被排到 14 名外（第1名 blk129=0.931 是错的）。同角色不同姿势行宽分布高度相似，几何特征区分不了。
- **内容级特征（去空格整块字形）→ 成功**：
  - 字符集合 Jaccard：blk64 第1（0.685，第2名 blk65=0.500）
  - 字符频次余弦：blk64 第1（0.990，第2名 blk65=0.959）
  两种内容指纹都稳定把岛风基准锁定到 blk64。

**由此定调**：
- 块 = mlt 的 SPLIT 条目（一个姿势块，多行完整立绘；库里 rows.blk=条目号）。正文块 = 用 line_meta_v2 kind 切出的连续 art 区段（24-26 行 art + 偶有 mixed/blank）。
- 特征应为**内容级**（整块字符构成：频次/集合/列锚点），不是几何级（行宽/跨度）。字符频次余弦最强（0.990）。
- 正文块比 DB 块短（正文 29 行 vs DB 45 行）：匹配必须容忍**行数差**——内容是子序列/近似而非整块 1:1 对齐。

**⚠️ 关键失败：内容级指纹区分不了「不同角色」（2026-09-05 原型实测，推翻上文"字符频次最强"的乐观结论）**
- 岛风正文块跑**全库(4角色)跨角色匹配**：top1 = 島風 blk64(cos=0.990)但 **top2-9 全被紲星あかり占据**(cos 0.972~0.960)，島風只占 top10 的 2 个；**纯字符频次余弦区分不了不同角色**——动漫少女立绘的字符构成类型高度相似（都是 `＼|/＿●○` + 少量台词字符），频次分布接近。
- **列锚点更糟**：岛风 blk64 排第 6（cos=0.422），被紲星あかり/鹿島压过——列锚点对**错位敏感**（列偏 1 格失配）反而比频次差。
- **根因**：跨角色区分需要「立绘具体形状差异」的指纹（感知哈希/轮廓矩/拓扑），charset 频次只够**同角色内分姿势**。
- **转型结论（重要）**：全局指纹做跨角色区分是伪命题。**务实路径 = 先锁定角色集（roles.json 素材统计/章节台词提及角色 → works filter）→ 角色内用内容级指纹分姿势**。这正是用户「先查角色后搜索」思路 + 用户已验证的 `--roles-filter` 缩库（見下）。

**原型 `scripts/tools/aahub_blockmatcher.py`（已建，可行+局限均实测）**：`load_blocks(db)` 按 mlt+blk 分组算 char_freq / `match_block(正文块, blocks)` 余弦排序 / `block_span` 几何指纹。**已验证**：岛风正文块(2406-2434)正确锁定 blk64(0.990)。**未验证**：块级对 entry_30179 全章性能/整章块切分——正文块切分用 line_meta_v2 kind，是下一步。

**待做（M3/M4）**：
1. 块指纹提取器（每 SPLIT 条目 char_freq/列锚点，入库 meta 新列或特征表）——原型已具雏形。
2. 块级匹配引擎：**先 role filter（works/roles）缩到该章角色 → 正文区块算特征 → 特征索引召回首选块 → difflib 精确认出精确行号+art 区**（保留 D1/B2 正确性）。
3. **跨角色是否走全局指纹 → 否**，已证伪；跨角色靠先锁角色集（不要重试字符频次/列锚点做跨角色）。
4. 性能：块级把匹配单元从 3207 行 → 几百块、每个块 1 次余弦 vs 每行 30 次 difflib，预计全章从 60s → 数秒（尚未实测验证）。

**角色级过滤缩库（已验证的关键性能杠杆，2026-09-05）**：`aahub_db.py --roles-filter "島風,鹿島,響・Верный,紲星あかり"`（build/build_sqlite 的 role_filter 参数，按 `parse_metadata` 推导的角色名过滤，绕过作品级 scope）→ 4 角色库 98,155 行（vs 全库 1182 万），**build 65s（vs 1926s）、加载+建倒排 4.3s（vs 全库 413s）、全章匹配 60.5s/19ms行（vs 806s+）**。角色名推导：`_detect_role` 目录段命中 roles.json 优先、否则 `norm_role_from_file`（`島風01（基本）.mlt→島風`、`響・Верный01...→響・Верный`）；響 在 AAHub 实际是 `駆逐艦/暁型/響・Верный`（非纯「響」目录）。**教训**：建小库用 `--roles-filter` + `--sqlite`，`load_from_sqlite(db, works=[AAHub作品名])` 或 `roles=[角色名]` 加载子集——切忌全库内存倒排。
