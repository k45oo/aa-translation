# AA 角色统一译名 + 术语表管理

> 适用于 `<repo>` 项目。角色统一译名需全局一致，跨作品复用。
> 详细方案：`doc/作品知识库合并方案_2026-08-27.md` + `doc/技能拆分方案_R18与术语表_2026-08-27.md`。

## 触发
- 角色统一译名（查维基/萌娘、加全局术语表、对已汉化文本做术语替换）
- 全局 + 作品术语表、作品知识库、人物候选（--full）与别名归并

## 一、角色统一译名（维基优先，2026-08-27 用户纠正）

**用户偏好（2026-08-27 最新指令，覆盖早前"萌娘百科优先"）**：查角色列表/统一译名**先查维基百科**——`zh.wikipedia.org/wiki/<作品>角色列表`（如《蔚藍檔案角色列表》），一次拿到日文原名+中文译名；**找不到（维基无该作品角色列表）再提示用户去萌娘百科**。用户原话："优先用 wikipedia 用 作品名+角色列表，找不到再提示我去萌娘百科找"。

**维基角色列表提取姿势（zh.wikipedia.org 实测）**：页面角色条目在 `<dt>` 标签，格式 `中文名（日文名）`——删 rt(读音)/rp/link/style 标签后取纯文本，括号前=中文名、括号内=日文名；中文名繁转简用 `zhconv.convert`（奥空綾音→奥空绫音）；加入 glossary.json 前先查已存在（避免重复），日文名冲突（同日文不同中文）必须 0。碧蓝档案实测：`蔚藍檔案角色列表` 提取 189 角色，zhconv 繁转简后全量入库。

**全局术语表 `<repo>\glossary.json`** 三处同步：
1. `角色` 数组（日文/中文/作品/分类/备注/别名）
2. `glossary` 替换对（翻译时强制统一译名，`_filter_glossary_pairs` 按作品语料过滤注入）
3. `known_names` 白名单（防残留误报）

**作品专属术语表**：`<作品>/work/glossary_<作品id>.json`（每作品独立）。**适用场景**：某替换对只对本作品正确（如 r401_metsubou アリス→愛麗絲，出自多娜多娜）。**编辑入口 = 各作品 work 页「作品术语表」区块**；**应用术语表替换（work 页）支持自选**（弹窗分组显示全局对+作品对）。注意：翻译管线 `aa_translate`/校对 `proofread` 只读全局 glossary.json，作品级替换靠工作台「应用术语表」落盘。

## 四、素材统计与别名归并

**素材统计防误判（2026-08-27，logic.py `_material_match_names`）**——素材名 → 匹配词集合规则：
- **排除单字符名**（len<2）：汉化文本行号前缀 `L<数字>` 大量碰撞
- **短名部分匹配**：术语表全名（久田泉奈）≠ 文本常用短名（泉奈）→ 基础名本身是匹配词 + `_jp_short_name` 提取日文名去姓短名
- **繁简变体**：爱丽丝↔愛麗絲（zhconv.convert 双向补词）；**仅日文后缀**「名（作品）仅日文」
- **作品别名匹配**：`_works_aliases()`（作品 id→别名缓存）
- **validate_glossary 重复检查排除 texture 分类**

**同一角色多译名（别名）归并（2026-08-28 定稿实施）**：`泄矢诹访子` 与 `青蛙子`（ケロちゃん）同一角色、译文两者保留，归并落在**素材统计 + 人物简介**（翻译注入 `_filter_glossary_pairs` 只读 `glossary` 替换对、**不读角色表**，故别名不进翻译注入）。**角色表加 `别名`（数组）字段**，`_material_match_names` 读它展开（青蛙子/ケロちゃん 并入泄矢诹访子），materials 只填规范名统计到全部变体，人物简介归并。保留变体独立条目（902 条不动），别名只放明确昵称（不放单字短名防误伤），不强扫全表随作品增量补。**候选层 `别名_of`**：glossary_candidates 角色候选可标 `别名_of`（人工填目标角色），promote 时 → 进全局角色表目标条 `别名`，不建独立人物；目标不在全局提示先promote主角色。详见 `references/2026-08-27-alias-field-design.md` + `references/2026-08-25-glossary-op-and-voice.md`。

## 五、对已汉化文本做术语替换

用 `aa_web_app.logic.apply_glossary_chapter(aa_path, tr_path, pairs, dry_run, backup_root)`（宽度自动校正 + 备份）。流程：dry_run 看效果 → `--apply` 实写 → 全量 scan_width 验证 0 错位。**坑**：
- 只替换全名（绁星あかり→绁星灯），**勿单独替换短名**（あかり 可能是标题/其他含义）
- 已译文本里的**错误译名要单独修**（akari_koikokoro 曾有「绫星あかり」错误译名 3 处）
- 替换后标题可能超宽（日文→中文更长）——用更紧凑措辞压宽，pad_to_width 只补不裁

### 变体替换：同一日文被译成多种中文（2026-08-30 新增）

**适用**：术语表替换只能匹配残留日文，但模型常把日文词（如 きらきー 人名）译成**多种中文变体**（闪闪/琪拉琪/kiraki/绮丽绮…），在汉化里找不到日文 → 术语表替换无效。**核心：以原文为锚点**，查原文对应汉化，把变体统一。

**流程（两步）**：
1. 提取变体（模型，`python aa_web_app/gen_variant_extract.py --work <id> --word <词>`）——把每行原文+译文喂模型，归纳该词被译成的所有中文变体，写 `work/variant_<词>.json`（变体+次数）供人工确认。实测 yukika_robot きらきー 得 162 变体；**坑**：模型遇整句会摘整句（"亚鲁欧从今天开始要和克莉琪一起生活"）当变体，且 变体→(章节,行号) 的 hit_map **行号与变体不符**（kiraki 46 命中行 0 行真含 kiraki）——故不按行号定位。
2. 替换（`python aa_web_app/apply_variant_replace.py --work <id> --word <词> --target <统一译名> --auto [--dry-run]`）——词根提取+无边界长词优先+**仅动原文含该词的行**（保险），宽度校正、超宽 SKIP 人工兜底，备份写 `work/backup/`。实测 yukika_robot きらきー→绮晶 200 处/28 文件，宽度 0 错位。

**关键设计**：①只替换**原文含 word 的行**（查原文替换对应汉化），杜绝在无该词的诗行/形容语境误伤（如"闪闪发光"若是形容词则不动）；②**长词优先**吃粘连（闪闪发光 先整串替换成绮晶，独立 闪闪 后替换）；③**中文人名带汉字后缀**（闪闪桑/kiraki桑/绮晶酱）用**无边界整串替换**（词边界正则 `(?![汉字])` 会漏掉后接汉字桑的昵称——2026-08-30 实测教训）；④拉丁词根（kiraki/Kiraki/kirari）用 `re.IGNORECASE`。

**扩展其他词**：改 `--word` 即可；同角色其他拼写（キラキー/きらきしょう/キラボット）需在原文词族层面确认（可能译为不同中文，如全名/机器人）——先 `--word` 各自提取再决定。

混合 reference 摘录（术语部分）：`2026-08-25-backend-low-zhipu-and-glossary-regex` 的术语正则示例、`2026-08-25-sujin-shabu-batch-and-term-replace` 的术语替换实战、`2026-08-26-r18-four-levels-and-wiki-roles` 的 wiki 角色提取 —— 见 R18 技能的对应 reference 文件（R18 为主导方，术语摘要已并入本节）

## 六、作品表 → 全局 反哺（2026-09-20）

**用途**：作品表某条已确认译名在别部作品也适用（同一 IP/同一人名），但全局表没有 → 以前只能手敲。
现成的三处入口（零 API、纯本地）：
- 共享实现 `scripts/common/glossary_repatriate.py`（`scan()` 列表 / `apply()` 写入 + 备份）
- CLI `python scripts/tools/gen_repatriate.py --work <id>`（列出）/ `--apply --select auto|cross|all`（`auto`=跨作品≥2 且非短词）/ `--terms a,b`
- 工作台 work 页「可反哺全局的条目」区块（`GET/POST /api/work/<id>/repatriate-list|repatriate-apply`）

**判据**：本作品表 `manual` 条目 − 全局差集（known_names ∪ glossary 对 jp/zh ∪ roles.json 日/中文/别名），归一 = 去空白+小写；
按**跨作品同名次数**降序（≥2 默认勾，单作品折叠），跑前先看跨作品分布——实测全库 455 个候选 term 里 91% 只出现在 1 部作品（=作品专属，反哺过去即污染）。

**写入去向（按类型）**：`cat=角色` → roles.json 新条目 + known_names；`cat=专名` → glossary.json 替换对（cat **必须** `特殊-专名`）+ known_names；
`re:` 开头 / 缺译名 / `zh==jp` / `FUNC_WORDS` 语法功能词 → 一律跳过。落盘前自动备份到 `.glossary_backup/<ts>/`（gitignore 已忽略）。

**三条机制铁律（读代码实测，反哺前必看）**：
1. **全局对只有 cat 前缀 `常用-` / `特殊-` 才会被 `gen_work_glossary.derive_auto` 派生到作品表**（`常用-` 全量注入、`特殊-` 语料命中才注入）。写 `cat:"专名"` = **永不派生 = 白做**；不给 cat = 代码默认 `常用-梗` = **全量注入每一部作品**（隐形地雷）。所以反哺专名统一用 `特殊-专名`。
2. **`re:` 对不注入 prompt**（`aa_translate.glossary_prompt_hint` 过滤）→ 短词(≤3 字)要安全就得包 `re:` 词边界，而包了就丢掉「让别部作品新翻译时就用对名字」的价值，只剩工作台本地替换。故**短词默认不勾**，由人工按嵌入率判断；写短词专名时自动包 `re:`（含汉字词再加汉字邻接守卫）。
3. **角色对派生 zh 恒为日文原文**（`アクア→アクア`），`_load_glossary_pairs` 又跳过 `auto+角色+zh==jp` → 反哺的角色在别部作品里只落**占位项（展示 `role_cn`，待人工确认）**，不自动改翻译。**反哺角色的收益 = 把名字推到别作品的待确认面上**，别期望自动统一。

**⚠️ 旁支 JSON 陷阱（反哺实现时踩到，2026-09-20）**：`work/` 下除真作品表外还有 `glossary_candidates.json`（AI 候选）与 `glossary_iter.json`（迭代层），**同 `glossary_` 前缀且字母序排在真表前** → `glob("glossary_*.json")[0]` 取到的是它们，读出来的"作品表"是空的（实测 **23 部作品**受影响，如 `中_学性奴隷日記` 反哺列表恒空）。**判据只能看数据结构**：`{"glossary": [...]}` 才是真表；取某作品表时优先同名文件、否则取第一份真表。

**短词嵌入率**：`glossary_repatriate.embed_rates()` = 该词在**所在作品语料**里被更长假名词夹住的比例。
判据 = 左邻假名 **或** 右邻假名且非正常接续（助词/断定/长音促音/敬称头字白名单）——
否则「ミクが来た」的 `が` 会被误判成嵌入（2026-09-20 口径修正，旧口径偏高 1.5~3.5 倍）。
实测：`リカ` 100%（全是 `アメリカ` 里的字 = line_classify_v2 段边界 bug 的碎片，bar_miku 的 `リカ→利口酒` 是脏数据，别反哺）、`ゆかり` 39%、`ミク` 27%、`アカネ` 25%、`カズマ` 15%。

**候选池差集口径（同批修复）**：`build_term_pool.load_known()` 现纳入**各作品表 manual+auto**（旧版只读全局、`work_id` 收了没用 → 作品表已确认的词会重新冒出来当候选）；
`gen_glossary_ai.load_existing()` 补读 roles.json；死代码 `extract_full`/`collect_all_batches` 已删。
差集含别部作品表 → 某作品表的脏映射会静默屏蔽别部候选，**逃生口 = 删掉作品表那行**。
方案+量测：`doc/方案归档/术语表反哺与候选池差集修复方案_2026-09-20.md`。

## 七、翻译前术语强制替换（2026-09-22 · 宝可梦链）

**触发**：某作品译名怎么都统一不了（角色名/道具名/招式名乱翻）时，别再往术语表里加 wiki 条目。

**铁律（用户 2026-09-22 指定）**：
1. **wiki 内容不进作品术语表、不注入 prompt** —— 注入实测无效：`entry_8342` 零 token 复核，同一词在已交付章里照样多种译法（ライナー→莱纳 39 次命中里 5 次乱翻；カズマ→和真 26 次里 11 次乱翻；きょううん→超幸运 13 次里 11 次乱翻；ギアソーサー 被音译成"齿轮索萨"）。
2. 改为**每章翻译前现查 wiki**（AA 术语 ∪ 官方译名对照）**∪ 作品术语表**，在**送模型的那份文本**上做**术语强制替换**。作品术语表只留人工条目 + 强制替换对。

**实现**：
- `scripts/common/pre_terms.py`：词源/章词语料过滤/单遍替换/缓存；`apply(text, base)` 是钩子入口，`apply_hits` 返回命中（`at` = 译名在**新文本**里的下标，报告高亮用）。
- `aa_translate` 三个拼装点接线（整行 body 首次+重试、mixed 段 job）+ `_install_pre_terms()`；`AA_PRE_TERMS=0` 关；生效范围由 `work_pipeline.is_pokemon(work)` 限定（非宝可梦作品零影响）。
- 验收报告 `python scripts/tools/gen_pre_terms_report.py --work <id> --base <eid>`（HTML，零 API）：A 词表 / B 逐行 原文→送模型文本 / C 固定表预填 / D 术语落地质量（正确/未译/疑似乱翻）。

**口径（宁可不替换，不落脏译名）**：`zh` 含假名或 `\ufffd`、`jp` > 20 字（句子）、`zh == jp`、单字词 → 不替换；长词优先 + 非重叠 + 短词片假名邻接守卫。**只改送模型文本**：原文、宽度 pad、art 列位校验、残留检测一律仍用原行（零宽度风险）。

**接线三坑（全部表现为"装了但整章零替换"，2026-09-22 连踩）**：
1. 钩子调用**不能写在文件末尾 `main()` 之后**——`main()` 先执行完，钩子从未装载。放在 `_install_pre_terms()` 定义之后即可。
2. 作品 id **必须显式传**（`fn(text, base, WORK_ID)`）：脚本方式跑时 `aa_translate` 就是 `__main__`，`import aa_translate` 拿到的是**第二份模块副本**（WORK_ID 空）→ 反查会解析成**别的作品**（实测解析成"白头与染灰魔女"）。`work_id()` 另补 `__main__` 兜底。
3. 管线判定**别只靠 `import work_pipeline`**：CLI 直跑时 sys.path 没有 `scripts/common` → ImportError 被 `except` 吞成 False。必须直接读 `work_meta.json` 兜底。
   验收 = 日志里出现 `[pre_terms] entry_xxxxx: 可用词 N（...）`；没有就是没生效。排查开关 `AA_PRE_TERMS_DEBUG=1`（打印每行 in/out）。

**坑**：
- 命中的 `at` 必须在**替换完成后**计算（逐对顺序替换时位置互相错位 → 预览页高亮切片把文本显示得"乱码"，实测踩过）。单遍实现：先收集跨度 → 同起点取长词 → 重叠跳过 → 再拼新文本。
- 短词左守卫**只防片假名邻接**（`(?<![ァ-ヺー・])`）：`アメリカ` 里的 `リカ` 要拦，但 `とカズマ` 的平假名多是助词，拦了就大面积漏替换。
- **校对（refine_aa）侧现在看不到 wiki 术语**（wiki 已移出作品表）→ 存在把已替换正确的名字改歪的风险；若真发生，给校对加术语白名单。

## 八、宝可梦 wiki 的补充术语 `补充术语.json`（人工增量 = 唯一手改入口，2026-09-22）

**铁律**：`doc/aa作品相关/ポケモンAA术语wiki/术语表.json` 与 `官方译名对照.json` 是**生成物**（`gen_pokemon_aa_wiki.py --build` 每次整体重写）→ **手写条目一律写 `补充术语.json`**，否则下次重建就丢。

```jsonc
{"terms":  [{"jp":"技マシン","zh":"招式学习器","cat":"道具","page":"补充（说明对齐）","note":"取舍理由"}],
 "works": {"<作品名>": {"terms":[{"jp":"ソノオスタジアム","zh":"花苑竞技场","cat":"场地","note":"ソノオタウン=花苑镇"}],
                         "effects":[{"jp":"《{竞技场}》のフィールド効果","zh":"《{竞技场}》的场地效果","cat":"场地模板"}]}}}
```

- **`terms` = 通用补充**：跨作品通用（`技マシン→招式学习器`、`持ち物→持有物`、`とくこう→特攻`、状态词 `怯み→畏缩/まひ→麻痹`）。**怎么捞**：ポケマス说明里 `effect`(日)/`desc`(中) 是平行文本，按 `「」『』《》` 成段对齐（段数相等才配）→ 就是「说明里早有中文、但缺日中对」的词。实测 2278 条可比、629 个候选对、318 个 jp 不在表里，人工筛出 24 条。
- **`works.<作品名>` = 作品专属项**：竞技场/队伍/地名只在单部作品出现，混进全局表会跨作品污染（同一假名别部可能对应不同中文）。**场地效果属于作品专属**（每部作品自带一套竞技场+场地效果）。
- **对翻译的影响**：`pre_terms.py` 读取（`src=wiki-补充` / `src=作品专属`），仍受**本章语料过滤**（本章没出现的词不替换）。**这两个来源允许整句（≤60 字）**，wiki 批量条目仍限 20 字——场地效果这类模板句才能整体落地。人工条目**优先于**生成的 wiki 条目（同 jp）：`wiki_pairs()` 里先 `extra_pairs()` 再读生成物，否则 src 标签会被覆盖成 `wiki-术语`、整句放行失效。
- **生成器要合并**：`stage_build()` 读 `OUT_DIR/补充术语.json`（同 jp 人工优先 + 追加新 jp），作品项统一 `cat='作品专属'` 进 `terms`，侧栏加 `补充`/`作品专属` 两个分类（`cats` 硬编码列表，`counts['补充']` 按 `_src` 计数）。
- **流程**：改 `补充术语.json` → `python scripts/tools/gen_pokemon_aa_wiki.py --build`（离线，只读 `_raw/`）→ pre_terms 缓存按 mtime 自动失效。验收：日志/`pairs_for()` 里出现 `wiki-补充`/`作品专属` 计数。
- **定名要用户确认**：作品专属的队伍名/造语（探検堂ミラクルズ→探险堂奇迹、電波局ストラッシュ→电波局猛击 之类）是**人工定名**，写进 wiki 前把候选列给用户确认，别自己冻结。地名一律先查 52poke（`api.php?action=query&list=search&srsearch=<日文名>` 取页面标题）——实测雷区：コトブキシティ=**祝庆市**（不是长寿）、ナギサシティ=**滨海市**（不是名木）、ノモセシティ=**野原市**、カンナギタウン=**神和镇**、ミオシティ=**水脉市**、ズイタウン=**随意镇**、ソノオタウン=**花苑镇**。

### 八.五、`修正` 段：抽取器踩坑的兜底（2026-09-22）

`补充术语.json` 的第三个段：`"修正": [{"jp":"チェイサー","desc":"…","effect":"…","src":"依据"}]` —— **按 jp 覆盖已有条目**（写哪个字段覆盖哪个），`--build` 时应用，重建不丢；未匹配的 jp 会打印警告。

**为什么需要它**（三种实测坑，全在ポテンシャル页）：
1. **`『X』付随` 是役割家族的「类型标记行」，不是说明**——旧抽取器把「付随」当说明 → `desc` 变「附带」（18 条，用户上报现象：汉化里 `『追击者』…　　附带效果`）。同类还有 `『エンペラー』は「Ｓ」ランク…`（正文句，被收成 `は「Ｓ」…`）、`『神槍』と呼ばれた…`（正文提及、半句）。
2. **`オリジナル技` 表里 AA 自己没填**（`effect = ---`，共 8 条：かまいたち/とける/フラッシュ/まるくなる/みやぶる 等）——说明得从别处捞：同页另一张表、人物手持ち表（`練紅玉.html` 有 `とける … 自分の「ぼうぎょ」を2段階上げる。`）、或官方（52poke 招式页的摘要句）。
3. 抽取器已修（**全局两遍**：先收带 `…`/`：` 分隔符的正条，再拿没分隔符的行只兜名字、`effect=''`）——名字不会丢（家族名 アシスト/キラー/野生 只能靠兜），垃圾说明不再进来；实测名字 0 丢失、10 条由「正文片段」变空。

**铁律：`desc` 会被当正文用**——`scripts/common/pokemon_fixed.py` 的 struct 轨命中章节行 `『名』…说明`（与 wiki `effect` 归一后逐字相等）时，**直接拿 wiki 的 `desc` 预填**并按源列位 pad。所以 `desc` 必须写**干净译文**：注释/「（※…）」/依据一律写 `src`，否則会原样进交付正文。实测 `entry_8695:1676` `・『追击者』…　　附带效果` 就是这么来的（当时 `desc="附带效果"`）。

**构建期体检**：`--build` 末尾打印 `⚠ 可疑 desc N 条`（占位串 / 比原文短太多 / desc 残留**平假名**连串 / 无说明行却还挂旧译文），清单里的 jp 直接粘进 `修正`。规则特意去噪：只算平假名（片假名常是专名）、引号内名字不算、`←` 之后的吐槽不算、去空白再比长度。当前 0 条。

### 八.六、`槽位` 段 = L2 模板/槽位规则表的字典（2026-09-23）

`补充术语.json` 的第四个段 `"槽位": {"分类":…, "类型":…, "范围":…, "接触":…, "效果":…}`——招式行等骨架行的槽位字典（人工可改，同键**以本文件为准**，改完即生效、无需 `--build`）。
规则模式（正则）在代码里（`scripts/common/pokemon_fixed.py` 的 `TPL_RULES`），数据在文件里。

**铁律：槽位取值必须「同宽短形」**——招式行在 AA 行里是**定列骨架**，替换后列位一动，
`aa_tm.guard` 的 art 锚点校验（±4）就拒（实测 `finalize` 报 `art`）。所以 `物`→`物`、`龍`→`龙`、`単`→`单`、
`霊`→`灵`、`ノ`→`普`、`闘`→`斗`（**不是**官方全称 `物理/幽灵/单体`，那样后面所有列都顶歪）。
已交付汉化里模型自己收敛到的写法就是短形（`物/龙/单/40/100/×`），与之一致即一致性目标。

**两条路径（同一套规则）**：
- **pre 轨**（`pokemon_fixed.match_line` 第 5 轨，规则 > 模板 > copy > 结构化 > 整行）：原文行直接出译文、**零模型**。触发条件：槽位全解析 + 覆盖后无假名残留 + 每个槽位译文不比原文宽；比原文窄的槽位**补全角空格到源 span 宽度**（`」`/`：` 跟着槽位一起换、补位放它后面）→ 列位不动才能过 art 校验。
- **post 规范化**（`normalize_tpl` → `pokemon_runner --normalize-only`，或通用链 rc=0 后自动跑）：把**模型译过**的行骨架拉回同一口径（`とくこう`→`特攻`、`鋼`→`钢`、`単`→`单`、`10割`→`10成`），正文一字不动；改动前整章备份 `work/backup_tpl_<ts>/`。

**三个已踩的坑**：① 招式名属**官方**译名，只查 `wiki_terms()`（AA 原创术语）会解析失败 → 整条落回模型（这就是"招式文本没替换"的根因）→ 单独 `tpl_terms()` = 官方译名对照 ∪ 传入 terms；② 逐行 `sorted(terms, key=len)` 会把 4000 条术语排 257 万次（全库扫描 56.7s）→ 按 terms 对象引用缓存键序；③ post 模式里「解不出的字段」= 已经是中文，**不算失败、原样保留**（当失败会让整行跳过，规范不了 `钢` 这类已译字段）。

**怎么确认生效**：`python scripts/works/pokemon_runner.py --work <id> --normalize-only`（打印改动行数 + 3 条样本 + 备份路径，重跑应为 0 行 = 幂等）；pre 轨看预填日志里的 `tpl N` 计数；单测 `scripts/tests/test_pokemon_fixed.py::TestL2Template`。

### 八.七、`模板` 段 = 整句模板（系统行零模型，2026-09-23）

`补充术语.json` 第五段 `"模板": [{"jp":"◎フィールド：《{场}》（>>{N}）","zh":"◎场地：《{场}》（>>{N}）","cat":"场地行"}]`——
骨架固定、只有槽位变化的**系统行**（场地行/出战/收回/潜能/场地效果/回复/战斗事件/踩陷阱/招式使用/状态栏）。
`pokemon_fixed.tpl_templates()` 编译成锚定正则（`{名}`→`(?P<gN>.+?)`），命中即整行零模型出译文；**加一条模板不用改代码**。

**为什么需要**：这类行此前无规则接管，全靠模型 → 时译时不译（用户上报 `◎カズマ` 给成 `◎卡兹玛`、
`◎フィールド：《…》` 整行照抄、`カエンチュは『熟達回復指令』を受け…` 半译）。

**三条护栏（都踩过坑，改模板前先读）**：
1. **槽位必须解析出中文**：`カズマ→和真`、`メジロマックイーン→目白麦昆` 这类只在**作品术语表**里，
   不在 wiki 里 → `work_glossary_terms()` 把作品表并入槽位术语表，否则 `{名}` 留日文 → 整行落回模型。
2. **输出零假名**（连单个 `の` 也拒）：实测 `◎直哉は「玉藻の前」を繰り出した！` 的 `{宝}` 未收录 →
   输出 `◎直哉派出了「玉藻の前」！`，把模型已译好的 `玉藻前` 顶掉。改 `_kana_left`（要求 ≥2 连）→ 不够，
   另加 `_kana_any`。
3. **宽度**：段尾补位到源宽（`pad_to_width` 同口径）——**不要逐段补位**，那会在 `《…》` 里塞满全角空格；
   比原文宽则整行交回模型。另：模板命中打 `no_art` 标记，`finalize()` 豁免 art 锚点那一条校验
   （`《》（）` 被 `aa_tm.guard` 当 art 锚点会误拒；宽度/残留/术语三条照旧）。

**存量修复**：`--normalize-only` 带**源行模板回填**——原文命中模板的行，汉化行一律取模板译文（改动前整章备份，
重跑幂等）。验证：`python scripts/works/pokemon_runner.py --work <id> --normalize-only`。

### 八.八、判定「替换后这行还需不需要翻译」= 残留片段判据（2026-10-08）

**流程铁律（用户指定）**：改替换规则/固定内容前，先按章出**渲染页把「需翻译 / 直出」逐行标出来**给用户人工确认
（`scripts/tools/gen_pre_terms_render.py` 已有「替换后 ↔ 原文」对照，扩它的逐行状态标记即可），确认后才动管线。

**判据（唯一可靠）**：把该行**被替换 / 模板 / 固定表覆盖的跨度**从原行里挖掉，剩下的片段（残留片段）
**含假名或汉字 → 需翻译**；只剩 ASCII / 标点 / 空白 → 不需翻译（本地直出）。逐行可解释，正好拿来渲染给人工看。

**为什么「无假名即直出」这类简判据全都不能用（三条实测）**：
- `◎今回の編成（戦闘準備：>>N）` **一个假名都没有**，整行仍是日文汉字（今回/編成/準備）→ 直出即漏译。
- `aa_translate.kana_runs`（残留检测器）**排除艺术假名 + 丢掉 <2 连**：`◎当スレwiki【…】` 的 `スレ` 被判成艺术假名
  → 判成「已无日文」。它只适合残留**检测**，不能当「已译完」的证据。
- `aa_translate.no_japanese()` 只判「行内有无 CJK」，**不区分「已替换成中文」与「仍是日文汉字」** → 它是给
  `AA_SKIP_NON_JP` 挡纯符号/ASCII 行用的，拿来判「替换后还需要翻译吗」必然把未译的汉字行放行。

**覆盖率 = 直出率**：某族要零模型直出，就得把它行内的日语内容 100% 覆盖（词条 + 模板）；缺一个词整行回模型。
所以补词要**按族成批**做（先量该族还有多少行没覆盖），别散着加。族清单/词源覆盖/零 API 摸底流程见
`references/pokemon-fixed-content.md`。

### 九.四点五、`术语表.json` 的 `desc`/`desc_zh` = 章节固定行的零模型出源（2026-10-08）

本作 wiki 的 `terms[]` 带 **`desc`（日文原文）+ `desc_zh`（中文）**，而**潜能/原创特性/原创招式条目的 `desc`
与章节行里的说明逐字一致**（归一空白后相等，例：章节行 `『エースキラー』…『エース』に与えるダメージを強化（1.5倍）する。`
↔ 条目 `desc` 同文，`desc_zh`「对「王牌」造成的伤害强化（1.5倍）。」）→ `『名』…　　　说明` 这类章节行可**零模型直出**，
且与 wiki 页面的中文口径自动一致。

**查表坑（必踩）**：潜能条目的 `jp` **带书名号**（`"jp": "『気合い』"`）——按裸名 `気合い` 查 **100% miss**
（实测 7708 行 struct 行全判「无覆盖」，误得「本作 wiki 毫无覆盖」的结论）。归一去空白后按**原样（含『』）**匹配，别 strip 括号。

**护栏**：`desc_zh` 是**生成物**（wiki 页面机翻后按 jp/zh 抽取，非人工确认）→ 落地前过残留假名/照抄检测
（同 `pokemon_fixed.guard` 的四重口径），不合格的交回模型。**覆盖缺口就是待办清单**：官方特性（本作 wiki 不收）无 `desc_zh`、
场地名（`カナズミジム` 之类）四源全无 → 名单单独出给人工确认，不要凭音译猜。

### 九.五、【角色名】批量提取→翻译→落库（2026-10-07 实测流程）

**用途**：作品里成百上千个说话人标签 `【名前】` 仍是日文时，一次性提取→翻译→落 `人工修正.json` 的 `本地译名`
（本作 wiki 唯一手改入口），比逐条查 wiki 快且可核对。

**步骤**（零 API 提取 + 分批翻译 + 一键落库）：
1. 提取：正则 `【([^】]{1,24})】` 扫 `aa/*.txt`，统计次数 + 记「首次出现原文行」当上下文；
   分类过滤掉纯艺术/骰值/小节标题（`（…）`、`の` 密集、含 `1D`、纯记号）。
2. 翻译前**先查已有译名源**，命中就照抄（口径一致优先）：本作 wiki `_raw/lines_zh.json`（最佳，含已定稿中文）
   > 全局 `roles.json`/`glossary.json` > 跨界角色原作官方中文名。**查不到不猜** → skipped。
3. 落库：合并所有批次 → 校验（zh 无假名、非原样、≤20 字）→ 写 `人工修正.json` 的 `本地译名`
   （`[["日文名","中文名"],…]`，已有条目优先不覆盖）→ `gen_work_wiki.py --work <id> --build`。
4. 验收用**行为口径**而不是词条口径：逐行 `pre_terms.apply_hits(line, base=…)` 看**标签真的变了**才算通过。
   只统计「标签整串能否作为一个词条命中」会误判——系统行（`【指示安価…】`）靠词级替换、标签整串本就不在词表里。
   实测 ポケの子：23,761 次标签 → **98.5%** 变化。

**两个必踩的坑**：
- **委派批量翻译要切小批（≤60 条/个）**：一次要求输出 200+ 条译名的长生成会把请求挂死（实测多次「等待模型响应」3000s+
  无响应，steer 也送不达因为它没有下一次工具返回）。同一批还要**禁 web_search、禁 terminal 循环 grep**（5MB 的
  `lines_zh.json` grep 会 180s 超时），改在 `execute_code` 里 `json.load` 到内存查。
- **≤2 纯假名的角色名必须显式 `允许` 才生效**（`补充术语.json` 的「歧义」段，同 `ヌシ→霸主`）：默认规则「≤2 纯假名
  无词界 → 不替换」会把 `【ミカ】`/`【デク】` 这类整块留在日文（实测 24 条里 21 条不生效）。`允许` 只豁免该默认规则，
  左右假名邻接守卫仍生效（`ミカン`/`ニコニコ`/`マイペース` 不受影响）；语义上真的是普通词的（`コレ`/`ママ`）不要授权。
  查生效：逐名取「首次出现的真实章节行」跑 `apply_hits`。
- **角色名与道具/常用词同形时要写「替译」，不能用无条件替换（2026-10-09）**：只写 `允许` 的角色名会把同形的另一义全吃掉
  ——`ラム`(角色 拉姆) 曾把道具简写 `ラム`(=木子果) 换成「拉姆」（已出货「卡比是拉姆」）。改法：`terms` 里的默认义 + 歧义条目
  `{"jp":"ラム","zh":"拉姆","require":"角色语境词表"}`（语境命中出 `zh`、否则出默认义）；词表要穷举全库站点标定，
  详见 `aa-manga-translation` 技能的「同形两义要用替译」条与 `doc/方案归档/宝可梦术语替换歧义守卫方案_2026-09-30.md` 第 6 节。

## 坑汇总
- **短词入全局术语表必须用 re: 词边界正则（2026-09-07 实测）**：`apply_glossary_chapter`/术语替换是**纯子串 replace 逐对遍历**（logic.py:659-670），短基酒词（ジン/ラム/ウイスキー/リキュール 等）裸入会把复合词改坏（ジンジャーエール→金酒ジャーエール、カカオリキュール→…利口酒、ピンク・ジン→ピンク・金酒，实测 200+ 处）。**修法 = 入表时用 `re:(?<![ァ-ヶー・])ジン(?![ァ-ヶー・])` 形式**（词边界=左右非片假名/长音/中黑），只替换独立词不碰复合词；且 re: 前缀会被 `glossary_prompt_hint` 过滤（aa_translate.py:1100）——只本地替换、不注入模型 prompt（模型本来就会译基酒词）。完整鸡尾酒名（モヒート 等不与他词复合）用普通条即可。**长词/复合词变体也要入表**（ジン・トニック 带点版 ≠ ジントニック 无点版，是不同子串）。
- **候选碎片根因已修（2026-09-07 line_classify_v2）**：见上条。修复=segment_line 加「词头 rescue」（DECOR_KANA/FACE_KANA 假名与相邻假名连串≥2 且非纯重复 → 整串改 text）；另外 extract_dialogue `_HEADER_A` 日期正则支持 2 位年（iitokolo_fc2 旧格式 `NNN ：作者 ：YY/MM/DD`，原 \d{4} 致楼主全 [?] 中断）。重跑：`python scripts/tools/line_classify_v2.py --work <id>`（全量重建 meta，从 raw html）→ `python scripts/common/extract_dialogue.py --work <id> --src --overwrite`（重建台词）。已修 case：ミルク→ルク/アメリカ→リカ/ヨーグルト→ーグルト/初音ミク→初音ク 等 905 处。
- **候选碎片根因 = line_classify_v2 segment 边界错位, 非分词工具（2026-09-07 实测）**：候选池里 モスコ/ルク/リカ/ルカ/マティー 等碎片不是 janome 切错（单测 リキュール/モスコミュール/マティーニ 均整词切出），而是 `work/line_meta_v2/<base>.json` 的 segments 把真台词里**单个假名误划进 art 段**——如 `ミルクをベースに` 被切成 `[55:56]art'ミ'` + `[56:68]text'ルクを…'`（ミ∈ART_KATA 被当装饰）、`アメリカのスラングで` 被切 `[98:99]TEXT'ア'` + `[99:100]art'メ'` + `[100:108]TEXT'リカ…'`。extract_dialogue 按残缺 segments 取 text 段 → 台词文件 `_台词.txt` 里已是 `ルクをベースに`/`リカのスラングで`（头字丢失）→ build_term_pool(janome) 分出的就是碎片。**换 Sudachi/MeCab/GiNZA 无效（数据在分词前已损坏）**；修应在 line_classify_v2 的 segment 切分（防把台词中段单假名判 art），或 extract_dialogue 对 mixed 行做「text 段头尾假名补全」后处理。排查法：台词行与原始 txt 同行对比（`L836_0 [?] ルク…` vs 原文 `ミルク…`）即暴露。
- glossary.json 数据结构：`角色` 条目字段 = 中文/作品/分类/备注/日文/别名(可选)；翻译注入只读 `glossary` 替换对

- 全部脚本从仓库根跑，模型配置在 `scripts/config/model_config.toml`
