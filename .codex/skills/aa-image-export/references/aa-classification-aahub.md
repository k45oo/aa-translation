# AA 行分类器现状与 AAhub 素材库应用方向（2026-08-14 探索，待用户定方向）

> 背景：嵌字方案 6 轮迭代后用户反馈"效果还可以，但存在 ①错误放大 AA 文字 ②没被放大的文本"。
> 追问分类器能否用 AAhub 素材库辅助——本文记录探索结论，方向未定，勿当已实现方案引用。

## 分类器现状（事实核查）
- `scripts/tools/line_classify_v2.py`（357 行）是**纯规则分类器，无 LLM、无视觉、无素材对比**：
  - `is_art_char(c)`：半角片假名/ASCII 标点/ART_SYMS/ART_KANJI → art；KANA_RE 假名/全角标点 → text
  - `_seg_counts`/`_has_dialogue`/`_max_real_dialogue_run`：连续段统计 + 置信度规则
  - 生成 `さーきー/work_fc2/line_meta_v2/<eid>.json`，含 kind/reason/segments[{start,end,kind,confidence}]
- **核心缺陷：`ART_KANJI` 艺术汉字黑名单（aa_common.py:23）手工枚举**，永远补不完：
  - 漏收（劜/芹/坏/斗匕/圦/仡心…）→ 画面汉字被当台词 → **误放大 AA**
  - 误收（真台词字）→ 台词字被当艺术 → **漏放大文本**
  - 两类问题同源，枚举思路是死路

## v2 分类器已沉淀的可靠信号（6 轮迭代验证）
- **reason 字段是分类金矿**：`no_dialogue` = v2 明确判纯画面（嵌字/加大绝不碰）；
  `lt`（文本过短）/`dotted`（点线文本）/`lz_mixed` = v2 承认有文本但可能判错型（才走中文兜底）
- v2 segments 中真台词段常标 `kind=None conf=None`（v2 未评估）——不能按"kind==text 且 conf≥0.5"过滤，
  要按"段含中文"判定；conf 0.55 是 mixed 行 text 段的常态值
- 汉化 txt 的连续中文（_HAN2_RE `[\u4e00-\u9fff]{2,}`）是渲染层最强的台词信号，但**不能单独用**：
  纹理行 `二二二二`/`八芹坏` 也含中文——需叠加 reason 过滤或纹理字排除

## AAhub 素材库（2.3G，从未被引用）
- 位置 `<repo>\AAhub\`（gitignored，词典性质）——**2026-10-10 已删除**（搁置方案收尾；重下 `https://dataset.aahub.org/datasets/mlt_v32_1.zip`）
- 结构：`2ch/`（やる夫系角色 AA，15023 个 .mlt）+ 五十音分类 + 汎用AA + 企业/人物等
- 格式：`.mlt` = Shift-JIS 编码，`[SPLIT]` 分隔多个角色帧；每帧 = 多行 AA 字符画
- **用途局限**：素材库存的是"角色多帧 AA"（整图），不是"行级 art/text 标签"——不能直接对比作品行

## 素材库应用方向（A/B/C 三案，推荐 A）
- **A. 统计驱动字符表（推荐）**：解析全部 .mlt（Shift-JIS→UTF-8），统计汉字在 AA 素材中的
  位置特征——素材里独立成帧片段（前后皆艺术符号）的汉字 = 艺术用字（二八从爻…）；
  连续 2+ 语义汉字成词（素材里几乎不出现） = 台词字。产出：自动扩充的 ART_KANJI +
  台词常用字白名单，替换手工枚举。一次离线解析几分钟，治本。
- **B. 行级指纹对比**：素材帧与作品行字符指纹相似度匹配。1.5 万帧 × 每行对比成本高，
  AA 变形多样，效果不确定——A 的过度版。
- **C. LLM/视觉辅助**：conf 0.5-0.7 区间行送视觉模型。每章几百行 × 73 章成本高且慢，
  违背"纯规则零 API"管线原则。
